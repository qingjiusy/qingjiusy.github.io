最开始
#

最近继续学 LLM 的时候，我有一个挺明显的感觉：只会调用模型 API，好像已经不太够了。

之前学 RAG、LangChain、Dify 的时候，我更多是在研究怎么把 LLM 接到一个应用里面。比如怎么检索文档，怎么组织 prompt，怎么调用工具，怎么把模型的回答放进一个业务流程里。

这些当然很重要。但最近看 Coding Agent 的时候，我发现还有一个更让我感兴趣的问题：

一个模型到底是怎么从“会聊天”，变成“能干活”的？

比如它怎么读一个代码仓库，怎么决定先看哪个文件，怎么修改代码，怎么运行测试，测试失败之后又怎么继续修。这里面真正有意思的地方，可能不只是模型本身，而是模型外面那一整套系统。

这套系统，就是我现在想学的 Harness。

我现在对 Harness 的理解还很初步，先粗暴一点说：它就是把 LLM 包起来，让它能在真实工程任务里行动的一套东西。里面会包括工具、上下文、权限、执行环境、验证机制、日志记录等等。

如果没有这些东西，模型就只是一个回答问题的人；有了这些东西，它才有机会变成一个能一步一步完成任务的 Coding Agent。

所以这篇文章先不写具体代码，也不假装自己已经很懂 Harness。更像是一个学习路线记录：我先看了哪几篇文章，它们分别让我理解了什么，以及我为什么想从一个 Mini Coding Agent 开始学起。

我先看了哪几篇文章
#

在正式动手之前，我觉得还是先把概念摸清楚一点比较好。不然很容易出现一种情况：框架 API 会调了，节点也会连了，但其实不知道自己为什么要这么设计。

所以我打算先从这三篇文章开始看。

Harness engineering for coding agent users
#

第一篇是 Martin Fowler 网站上的 Harness engineering for coding agent users。

这里稍微注意一下，这篇文章不是 Martin Fowler 本人写的，作者是 Birgitta Böckeler。只是发布在 Martin Fowler 的网站上，所以我后面一般会把它叫做 Fowler 网站上的 Harness Engineering 文章。

这篇文章给我的感觉是，它比较适合用来建立大局观。

它不是一上来就说某个 agent 框架怎么用，而是在讨论：如果我们想让 Coding Agent 少一点人工盯着，也能更可靠地完成任务，那我们应该在模型外面加什么东西。

里面让我印象最深的是两个词：guide 和 sensor。

Guide 可以理解成“提前引导”。比如：

  • 项目规则
  • 架构文档
  • 代码风格
  • 测试说明
  • AGENTS.md 这类给 agent 看的工作规则

这些东西的作用是，在 agent 开始干活之前，尽量把它往正确方向上带。

Sensor 可以理解成“事后检查”。比如：

  • lint
  • typecheck
  • 单元测试
  • 静态分析
  • 日志
  • 代码 review
  • 浏览器截图或运行结果

这些东西的作用是，在 agent 做完某一步之后，尽快发现它有没有跑偏。

这个观点对我挺有启发的。因为之前我看 LLM 应用时，很容易把注意力放在“模型够不够强”“prompt 写得好不好”上。但这篇文章提醒我：真正的工程系统不能只靠模型自己发挥，还要设计一整套引导和反馈机制。

换句话说，Harness 不是让模型一次性变聪明，而是让系统能不断把模型往正确方向推。

如果以后我自己做 Mini Coding Agent，这篇文章对应到实践里，大概就是两件事：

  1. 在 agent 做事前，给它足够清楚的项目规则和任务上下文。
  2. 在 agent 做事后，用测试、lint、diff、日志这些东西检查它有没有真的做对。

The Anatomy of an Agent Harness
#

第二篇是 LangChain 的 The Anatomy of an Agent Harness。

这篇对我来说更像是“拆结构”。它有一个很直接的说法：Agent = Model + Harness。

这个表达挺好理解。Model 是模型本身，Harness 则是模型外面那一整套让它能工作的机制。比如：

  • agent loop
  • tool calling
  • filesystem
  • sandbox
  • memory
  • search
  • context management
  • middleware
  • tracing

也就是说，一个 agent 能读文件、运行命令、保存中间结果、使用工具、继续根据错误修复，并不是因为模型天然就拥有这些能力，而是 Harness 把这些能力包装成了模型可以调用的东西。

这篇里面我觉得最重要的是 filesystem 和 sandbox。

Filesystem 让 agent 有了一个可以读写的工作空间。没有文件系统的时候，用户只能把内容复制粘贴给模型；有了文件系统之后，agent 才能自己读代码、改代码、保存中间结果，甚至通过 Git 追踪改动。

Sandbox 则是让 agent 能在一个相对安全的环境里运行命令。毕竟让模型随便在本机执行命令还是挺吓人的（笑）。所以真正的 Harness 不能只考虑“能不能执行”，还要考虑“在哪里执行”“能访问什么”“哪些命令允许跑”“失败结果怎么反馈给模型”。

这篇文章让我更明确地意识到：Harness 不是一个很玄的概念，它其实可以被拆成很多很具体的工程模块。

所以我之后如果写 Mini Coding Agent，也不应该一上来就追求很复杂的智能，而是先把这些基础模块拆开：

  • 先有一个最小 agent loop。
  • 再有几个基础工具，比如读文件、写文件、搜索代码、运行命令。
  • 然后加权限限制和执行环境。
  • 最后再加验证和 trace。

这样一步一步搭起来，应该比一开始直接学一个大框架更容易理解。

Agent Harness Engineering
#

第三篇是 Addy Osmani 的 Agent Harness Engineering。

这篇给我的感觉更偏工程实践。

前两篇更多是在帮我理解 Harness 是什么、由哪些东西组成。而 Addy 这篇更像是在提醒我：agent 出错的时候，不要只说“模型不行”，而是要反过来想，我的 Harness 哪一层没有设计好。

比如 agent 经常改错文件，那可能不是简单地怪模型不聪明，而是：

  • 文件搜索工具给的信息不够准？
  • 上下文里没有项目结构？
  • 没有限制它能修改的目录？
  • diff 检查太弱？

比如 agent 跑测试失败之后不知道怎么修，也可能不是模型完全不会，而是：

  • 测试日志太长，直接把上下文冲烂了？
  • 错误信息没有被压缩成模型容易理解的格式？
  • verifier 没有把失败原因说清楚？
  • agent loop 没有设计好重试流程？

这个思路我觉得很重要。因为它把问题从“调 prompt”推进到了“调系统”。

如果我以后自己做一个 Mini Coding Agent，它失败是很正常的。关键不是失败本身，而是我能不能从失败里看出来：应该补一个工具？应该加一个权限？应该改一下上下文结构？还是应该增加一个验证步骤？

这也是我觉得 Harness Engineering 有意思的地方。它不只是让模型回答得更好，而是把模型的失败变成系统改进的线索。

所以 Harness 到底是什么
#

看完这几篇之后，我现在对 Harness 的理解大概是这样：

Harness 是模型外面那套让模型可以完成任务的工程系统。

如果只看一个普通聊天模型，它大概是这样：

用户输入
↓
模型回答

但如果是一个 Coding Agent，它更像是这样：

用户任务
↓
构建上下文
↓
模型决定下一步
↓
调用工具
↓
观察工具结果
↓
继续行动
↓
运行验证
↓
失败就修复，成功就总结

中间这些“构建上下文”“调用工具”“观察结果”“运行验证”“失败重试”“记录轨迹”，都可以算是 Harness 要处理的事情。

所以我现在不会把 Harness 理解成某一个具体框架。它更像是一层工程抽象。

具体到 Coding Agent，Harness 可能包括：

  • Agent Loop：让模型可以多轮思考、行动、观察，而不是只回答一次。
  • Tool System：把读文件、写文件、搜索代码、运行命令这些能力包装成工具。
  • Permission System：限制 agent 能访问什么、能改什么、能执行什么。
  • Context Management：把任务、规则、相关文件、错误日志整理成模型能用的上下文。
  • Sandbox：给 agent 一个安全的执行环境。
  • Verification：用测试、lint、typecheck、diff 检查结果。
  • Trace：记录每一步发生了什么，方便之后分析失败原因。

这里我觉得最关键的一点是：Harness 不是为了替代模型，而是为了让模型更像一个可以被工程化使用的组件。

模型负责生成和推理，Harness 负责提供环境、边界和反馈。

我的学习路线
#

按照现在的理解，我觉得接下来可以分成几个阶段学。

第一阶段，先补概念。

这一阶段主要看上面提到的三篇文章，把 Harness、Agent、Agent Loop、Tool、Sandbox、Context、Verifier、Trace 这些词先分清楚。目标不是背定义，而是能用自己的话说清楚：一个 Coding Agent 为什么不是单纯的模型调用。

第二阶段，手写最小 Agent Loop。

先不管复杂框架，只实现一个很小的循环：

model -> tool call -> tool result -> model -> ...

这一阶段重点是理解 ReAct 这类模式背后的基本流程：模型先决定要做什么，然后调用工具，观察结果，再继续下一步。

第三阶段，做 Tool Harness。

也就是把 read_file、write_file、search_text、run_command 这些工具做得稍微像样一点。这里重点不是工具数量，而是工具边界。

比如路径限制、危险命令拦截、输出截断、错误信息格式化，这些都要开始考虑。

第四阶段，做 ContextBuilder。

我不想把所有东西都乱塞进 prompt 里，而是希望整理成结构化上下文，比如：

[Task]
当前任务是什么

[Project Rules]
项目规则是什么

[Relevant Files]
相关文件有哪些

[Recent Tool Results]
最近工具调用结果是什么

[Failures]
当前失败信息是什么

[Output Contract]
最后需要怎么回答

这样做的目的，是让模型拿到的上下文更清楚，而不是在一大坨文本里自己找重点。

第五阶段，加入 Verification。

agent 改完代码之后，不能直接结束。至少应该跑一些检查，比如：

  • git diff
  • npm test
  • npm run lint
  • npm run typecheck

当然具体命令要看项目类型。重点是让 agent 有一个反馈闭环：失败了就把错误信息整理好，再让它继续修。

第六阶段，加入 Trace。

我要记录每一轮发生了什么，比如：

  • 模型输入了什么
  • 模型输出了什么
  • 调用了哪个工具
  • 工具参数是什么
  • 工具结果是什么
  • 哪个验证失败了
  • 最后改了哪些文件

因为真正调 agent 的时候，最难受的不是“它错了”，而是“不知道它为什么错”。Trace 的作用就是把这个过程摊开，让之后能分析失败原因。

最后，再回头看框架和源码。

等自己手写过一个 Mini Harness 之后，再去看 LangGraph、Claude Agent SDK、OpenAI Agents SDK、OpenHands、SWE-agent、Aider 这些东西，应该会更有感觉。

到那个时候，我希望自己不是只会说“这个框架很好用”，而是能看懂它为什么这样设计。

总结
#

这篇先算是一个起点。

我现在对 Harness 的理解还不算深入，但大概已经能感觉到：它不是一个单纯的新名词，也不是某个框架的专属概念，而是 LLM 变成 Agent 时绕不开的一层工程系统。

如果说以前学 RAG、LangChain，更多是在学怎么把模型接进应用；那接下来学 Harness，我更想学的是：怎么让模型在一个有工具、有上下文、有权限、有验证、有反馈的环境里完成任务。

所以我的路线暂时不会从复杂 multi-agent 开始，也不会一上来啃一堆论文。而是先从一个很小的 Mini Coding Agent 开始。

先让它会读文件、改文件、跑命令、看错误。

然后再慢慢加权限、上下文、验证和 trace。

这条路看起来可能没有直接套框架那么快，但我觉得会更适合我现在的学习状态。毕竟我真正想补的不是“又学会一个框架”，而是理解 Coding Agent 背后的工程系统。

下一篇如果顺利的话，就开始动手写这个 Mini Coding Agent。
