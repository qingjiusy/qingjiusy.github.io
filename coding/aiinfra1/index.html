2. Python：从脚本到工程
#

2.1 名字、对象与引用
#

Python 变量更准确的说法是“名字绑定到对象”。赋值通常不会复制对象，只会建立新的引用：

a = [1, 2]
b = a
b.append(3)

print(a)        # [1, 2, 3]
print(a is b)   # True：指向同一个对象
print(a == b)   # True：值相等

需要区分两个运算：

  • is 比较对象身份，适合写 x is None；
  • == 调用值比较逻辑，比较“内容是否相等”。

函数参数同样是名字绑定。函数收到的是对象引用，不是“按引用传递”或“按值传递”这两个传统标签中的任意一个：

def mutate(xs: list[int]) -> None:
    xs.append(1)          # 修改调用方可见的同一个列表

def rebind(xs: list[int]) -> None:
    xs = [1,2]              # 只让局部名字 xs 指向新列表

data: list[int] = []
mutate(data)
print(data)               # [1]

rebind(data)
print(data)               # 仍然是 [1]

这套模型能解释大量常见 Bug：默认可变参数、浅拷贝、缓存污染以及多线程共享状态。

这些改变通常属于修改原对象：

xs.append(1)
xs[0] = 100
xs.clear()
xs.extend(...)

这些属于重新绑定局部变量名：

xs = []
xs = [1, 2]
xs = another_list

同时还要记住：Python 对象的生命周期取决于“还有没有引用指向它”，而不是创建它的那个函数是否已经结束。

2.2 可变对象、不可变对象与拷贝
#

常见不可变对象包括 int、float、bool、str、bytes 和元素均不可变时的 tuple；常见可变对象包括 list、dict、set 和大多数自定义实例。

如果 x 和 y 引用同一个可变对象，那么通过其中一个变量原地修改对象时，另一个变量也能看到变化；但重新赋值只会改变变量自己的引用。

默认参数只创建一次
# 

# 错误：同一个列表会被多次调用共享
# 里面的 [] 不是“每次调用都生成一个新列表”，而是：
# Python 执行到这个 def 时创建一个列表对象，之后所有没有传 result 的调用，都共享这个列表。
def collect_bad(x: int, result: list[int] = []) -> list[int]:
    result.append(x)
    return result

# 正确：用 None 表示“未提供”
def collect(x: int, result: list[int] | None = None) -> list[int]:
    if result is None:
        # 没有修改某个共享对象
        # 而且每次调用都有自己独立的局部变量 result
        result = []
    result.append(x)
    return result

默认参数只会在函数定义时求值一次，得到的对象会被保存下来，后续调用不会重新求值。

因此上面的代码如果我们去使用，输出是这样的：

print(collect_bad(1)) # [1]
print(collect_bad(2)) # [1, 2]
print(collect_bad(3)) # [1, 2, 3]

这是因为从我们定义函数以后，默认参数， result 的默认列表对象已经在函数定义时创建，之后每次调用collect_bad都只是在对同一个对象进行 append 操作。

浅拷贝与深拷贝
# 

import copy

src = [[1], [2]]
shallow = src.copy()           # 只复制最外层列表
deep = copy.deepcopy(src)      # 递归复制内部对象

shallow[0].append(9)
print(src)                     # [[1, 9], [2]]
print(deep)                    # [[1], [2]]

深拷贝并非默认答案。对大型张量或模型状态做无意复制可能产生巨大的内存和时间开销。更好的做法是先明确：哪些数据需要独占，哪些可以只读共享。

2.3 作用域、闭包与 LEGB
#

Python 按 LEGB 顺序查找名字：Local（局部）→ Enclosing（外层函数）→ Global（模块）→ Builtins（内置）。

闭包(闭包 = 一个函数 + 它所保存的外层作用域变量)会保留对其所需外层变量的引用，因此即使外层函数已经执行结束，这些变量仍然可以被内部函数访问：

from collections.abc import Callable

def make_multiplier(scale: float) -> Callable[[float], float]:
    def multiply(x: float) -> float:
        return x * scale
    return multiply

double = make_multiplier(2.0)
print(double(3.0))  # 6.0

从上面这段代码我们就看出：函数 multiply 被返回以后，虽然 make_multiplier 已经执行结束了，但 multiply 仍然“记得”当时外层函数里的 scale。 在这里，返回出来的 multiply 就是一个闭包。double = make_multiplier(2.0)得到的是一个“带着 scale=2.0 环境的函数”。

闭包最重要的意义，就是函数可以“携带状态”。

循环中创建闭包时要注意延迟绑定：闭包在调用时才读取外层名字。

# 三个函数最终都读取同一个 i，结果都是 2
# 在这里，bad里面放了三个lambda函数
# bad[0]是“取出第一个函数”，bad[0]()是“调用第一个函数”
bad = [lambda: i for i in range(3)]
print([fn() for fn in bad])  # [2, 2, 2]

# 用默认参数在每轮定义时保存当前值
# 这里成功的关键就在 “默认参数是在函数创建时就确定的”
# 所以这里使用默认参数，相当于“把当前值冻结下来”。
good = [lambda i=i: i for i in range(3)]
print([fn() for fn in good])  # [0, 1, 2]
print([fn(1) for fn in good]) # [1, 1, 1]

对于列表中放函数这件事，你可以理解为函数本身就是对象，所以当然可以放进列表。

对于上面的代码的现象的解释：lambda: i 创建函数时，并不会把“当前的 i 的值”复制进去；它只是记住“以后调用时去找这个 i”。但是真正调用的时候（也就是[fn() for fn in bad]），循环早就结束了，那个被三个函数共同引用的 i 已经变成 2。这就是所谓的：延迟绑定（late binding）

而这里的 good 函数则等价于：

good = [
    lambda i=0: i,
    lambda i=1: i,
    lambda i=2: i,
]

之后print([fn() for fn in good])每次都是空参数调用 fn()，因此会使用各自保存的默认参数。

岔开来介绍一下lambda函数：你可以把它理解为一种用一行代码写“小函数”的方式。

基本语法是：lambda 参数1, 参数2, ...: 返回的表达式

再举个例子，lambda i=i: i就等价于：

def f(i=i):
  return i

平时如果函数只是读取外层变量，直接读取即可（因为有闭包）。但是如果需要重新绑定外层函数作用域里的名字，使用nonlocal（因为如果外层变量指向的是可变对象，比如 list/dict，只是 append 或修改内容，则不需要 nonlocal）；要更改全局变量则使用 global。虽然 nonlocal 和 global 可以改外部状态，但不要滥用。

# 会报错，因为这里在 inner 里写 count = ...
# Python 会把 count 视为 inner 自己的局部变量。
# 但是由于它还没在 inner 里被赋值，所以报错。
def outer():
    count = 0

    def inner():
        count = count + 1

# 正确写法
# 通过nonlocal count
# 说明这个 count 不是我 inner 自己新建的局部变量，我要修改的是外层函数里的那个 count
def outer():
    count = 0

    def inner():
        nonlocal count
        count = count + 1
        return count

    return inner

f = outer()

print(f())  # 1
print(f())  # 2
print(f())  # 3

2.4 类、数据模型与协议
#

Python 的特殊方法让对象接入语言协议（让自己定义的对象，支持 Python 原生的操作方式）。例如，实现 __len__ 后可调用 len(obj)，实现 __iter__ 后可被 for 遍历。Python 不是要求你的对象必须属于某个具体类型，而是看它有没有实现对应的行为。

因此举一个例子：

# 在这里 A 实现了 Python 关于“长度”这件事的协议
class A:
    def __len__(self):
        return 5

# A() 是“根据这个类创建出来的实例对象”
a = A()
# 所以 a 可以被 len(a) 这样使用
print(len(a)) # 5

再来看一个例子：

from dataclasses import dataclass
from collections.abc import Iterator

# 这里的 @dataclass 帮你自动写了初始化代码
# 近似于：
# class Batch:
#   def __init__(self, samples: list[list[float]]):
#       self.samples = samples
@dataclass
class Batch:
    samples: list[list[float]]

    def __len__(self) -> int:
        return len(self.samples)

    # 这个 __iter__() 方法会返回一个迭代器对象，而这个迭代器每次取出来的元素类型是 list[float]
    def __iter__(self) -> Iterator[list[float]]:
        return iter(self.samples) # iter 真正创建并返回迭代器

batch = Batch([[1.0, 2.0], [3.0, 4.0]])
print(len(batch))
for sample in batch:
    print(sample)

其中 @dataclass 是 Python 提供的类装饰器，主要用于简化“以保存数据为主的类”的写法。它根据类中声明的字段，自动生成 init、repr、eq 等常用特殊方法，减少样板代码。

Iterator[T] 表示“迭代器类型”，其中 T 是每次调用 next() 时返回的元素类型。Batch 本身更准确地说是“可迭代对象”，因为它实现了 iter；真正的迭代器是 iter(self.samples) 返回的对象。具体关于这一块我们在 2.5 中介绍。

常见特殊方法及用途：

方法 触发方式 典型用途
__init__ 创建实例后 初始化实例状态
__repr__ repr(obj)、调试器 无歧义的调试表示
__call__ obj(...) 让实例表现得像函数
__enter__ / __exit__ with 管理资源生命周期
__iter__ / __next__ for、next 定义迭代协议
__getitem__ obj[key] 索引、切片或映射访问

实例方法、类方法和静态方法
#

定义在类里面的方法，并不都是同一种方法。

  • 实例方法：操作某一个具体对象，第一参数通常是 self；
  • 类方法@classmethod：操作“这个类本身”，第一个参数通常是 cls，常用于备选构造器；
  • 静态方法@staticmethod既不自动拿实例，也不自动拿类，更像是“放在类里面的普通函数”
# @dataclass 帮你自动写了初始化代码
# 近似于：
# class Device:
#   def __init__(self, kind: str, index: int):
#       self.kind = kind
#       self.index = index
@dataclass
class Device:
    kind: str
    index: int

    # 类方法
    # 对于用 @classmethod 定义的方法，第一个参数会由 Python 自动传入“当前类本身”
    # cls 不是 Python 关键字，可以改名，但按照惯例类方法的第一个参数都写成 cls，用于接收当前类本身
    @classmethod
    def parse(cls, value: str) -> "Device":
        kind, index = value.split(":")
        return cls(kind=kind, index=int(index))

device = Device.parse("cuda:0")

@classmethod表示这是一个类方法。调用 Device.parse(...) 时，Python 会自动把 Device 类本身传给第一个参数cls。

parse() 的作用是把类似 “cuda:0” 的字符串解析成 kind=“cuda” 和 index=0，然后通过 cls(...) 创建并返回一个新的 Device 实例，因此它属于一种备选构造器。

2.5 迭代器与生成器：按需生产数据
#

可迭代对象能返回迭代器；迭代器保存遍历状态，并通过 __next__ 逐个返回元素。

比如nums = [10, 20, 30]就是一个可迭代对象，它提供“从头开始遍历”的能力；而iter(nums)会返回一个迭代器，它保存遍历状态，知道“上一次取到哪里了，下一次应该取哪个”；然后这个迭代器可以被next(iterator)一步一步消费，底层会调用__next__()逐个返回元素(__next__()是迭代器对象内部实现的特殊方法)，元素耗尽时抛出 StopIteration：

nums = [10, 20, 30]

it1 = iter(nums)
it2 = iter(nums)

print(next(it1))  # 10
print(next(it1))  # 20

print(next(it2))  # 10

生成器函数是编写迭代器的简洁方式。调用生成器函数不会立刻执行函数体，而是返回一个生成器对象；这个生成器对象本身就是一种迭代器。：

from collections.abc import Iterator

def read_batches(path: str, batch_size: int) -> Iterator[list[str]]:
    batch: list[str] = []
    with open(path, encoding="utf-8") as file:
        for line in file:
            batch.append(line.rstrip("\n"))
            if len(batch) == batch_size:
                # yield：把当前的 batch 交出去，但不要结束函数
                # 这时候调用方拿到了数据，但是函数会暂停在这里
                # 这和 return 有本质区别
                yield batch
                batch = []

    # 这个if的存在是因为文件行数不一定刚好能被 batch_size 整除
    # 这是为了把最后不足一个完整 batch 的数据也交出去
    if batch:
        yield batch

# 一个具体的使用例子
for batch in read_batches("data.txt", 100):
    print(batch)

# 一个不好的做法，因为这样会把每个batch都存下来，根本就没有起到节省内存的作用
batches = []
for batch in read_batches("data.txt", 100):
    batches.append(batch) # batches[idx]会指向每一个batch，这样最终会把所有 batch 都累积到内存里，失去了流式处理的主要优势。

只要函数里出现 yield，这个函数就不再是普通函数，而是“生成器函数”。以前如果你想自己写一个迭代器，可能要自己实现：iter()，next()。还要自己保存：“我现在遍历到哪里了？”而使用生成器函数的话，每次 next() 执行到 yield 时返回一个值并暂停，下次 next() 从暂停位置继续。生成器因此可以按需逐个产生数据。

由于yield 返回一个值后暂停函数，下一次迭代从暂停位置继续。与一次性构造完整列表相比，生成器的峰值内存通常只与一个批次相关（生成器不会一次性把所有数据都放进内存，内存里通常只需要同时保留当前这一批），适合流式数据管线，比如：

  • 大文件读取
  • 数据集训练
  • 日志处理
  • 网络数据流
  • AI / ML 数据管线

需要记住：

  • 生成器通常只能消费一次，遍历结束不会自动回到开头。；
  • 惰性求值会把异常推迟到迭代时； 
    def gen():
    yield 1
    x = 1 / 0
    yield 2

g = gen() # 不报错
next(g) # 得到 1
next(g) # 报错
  • 把生成器转成 list 会重新物化所有元素，list(generator) 操作会一次性取出并保存所有元素，失去节省内存的优势。

另外，来说明一下for 循环的底层逻辑和如果不用 yield，自己去写一个可迭代对象的做法：

# 下面的逻辑就等于：for i in x:
iterator = iter(x)       # 调用 x.__iter__()

while True:
    try:
        i = next(iterator)  # 调用 iterator.__next__()
    except StopIteration:
        break

    ...

意味着如果不用生成器函数，一个对象 x 想要被 for 循环遍历，就需要支持迭代协议：iter(x) 能返回一个迭代器。这个迭代器再通过 __next__() 逐个返回元素。

list 能被 for 遍历，是因为它能返回一个迭代器；真正负责 __next__() 的是这个 list 迭代器。

2.6 装饰器：在调用边界附加行为
#

装饰器接收一个可调用对象，并返回另一个可调用对象。 简单的理解装饰器就是：传入一个函数，返回一个新函数，用新函数把原函数包起来。 下面的计时器保留了原函数的元信息：

from collections.abc import Callable
from functools import wraps
from time import perf_counter
from typing import ParamSpec, TypeVar

P = ParamSpec("P") # 表示一个函数的整套参数
R = TypeVar("R") # 表示一个暂时不知道是什么的返回类型

# 包装函数，实现了计时功能
def timed(fn: Callable[P, R]) -> Callable[P, R]:
    # @wraps(fn)可以删掉 功能依旧能跑 只是可能最后print打印名字的时候会出错
    @wraps(fn) # 把原函数的一些信息复制给 wrapper，比如__name__，__doc__等等
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        start = perf_counter() # 记录当前时间
        try:
            # 一个典型的闭包，因为fn是外层函数 timed 的局部变量
            return fn(*args, **kwargs)
        # 在python语法中，在真正返回之前，一定先执行 finally
        # 使用 try/finally 后，即使 preprocess() 报错，依然可以打印，然后 Error 继续向外抛。所以写 finally 更加稳健
        finally:
            elapsed_ms = (perf_counter() - start) * 1_000
            print(f"{fn.__name__}: {elapsed_ms:.3f} ms")
    return wrapper

@timed
def preprocess(values: list[float]) -> list[float]:
    return [value * 2 for value in values]

当python看到：

@xxx
def foo():
    ...

它就理解成：

def foo():
    ...

foo = xxx(foo)

另外注意，xxx(foo)是在定义 foo 的时候就执行的，而 foo 函数体本身，要等到后面真正调用 foo() 时才执行。

所以这里的@timed 等价于 preprocess = timed(preprocess)。functools.wraps 会保留函数名、文档字符串等属性，这对日志、测试和框架反射很重要。

def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:表示了 wrapper 接收的参数，和 fn 接收的参数一致；wrapper 返回的类型，也和 fn 一致。

这一段其实就是包装原函数的核心：

def timed(fn):
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)

    return wrapper

解释一下*args 和 **kwargs：

如果 wrapper 写成 def wrapper(values):，那么它只能包装这种函数：def foo(values):。 但装饰器通常希望什么函数都能包装。所以写成def wrapper(*args, **kwargs):，就是不管原函数有多少位置参数、关键字参数，我全部接住。

装饰器适合日志、缓存、权限检查和性能观测，很适合复用；如果只是单个调用点需要计时，一个普通的 with timer(): 往往更直白，不必为了“高级”而使用装饰器。

因为装饰器不仅是为了复用，也是为了把某种行为绑定到函数本身；with 更适合绑定到某一段代码执行范围。

2.7 上下文管理器：让资源必定释放
#

with语法的核心作用可以理解为：进入一段代码前做一件事，离开这段代码后一定再做一件事。

from contextlib import contextmanager
from collections.abc import Iterator
from time import perf_counter

@contextmanager # 它把一个普通的带 yield 的函数，变成了一个可以给 with 使用的东西
def timer(name: str) -> Iterator[None]:
    start = perf_counter() # 用来掐表的高精度测时间的函数
    try:
        yield
    # 有finally的存在，保证try里面不管正常还是报错，我这里都一定执行（但是如果try前面更早有报错的话，finally不会执行）
    finally:
        elapsed_ms = (perf_counter() - start) * 1_000 # 计算执行的时间（开始和结束的间隔值）
        print(f"{name}: {elapsed_ms:.3f} ms")

# 在这里的执行顺序是：进入 with -> 开始计时 -> 执行with里面的代码 -> 离开with -> 结束计时 
with timer("load data"):
    data = [value for value in range(100_000)]

一般来说，python如果想要一个对象 x 支持with x:，这个对象需要去实现__enter__()，__exit__()。但是写这两个函数还是有点麻烦。所以我们可以使用@contextmanager，让我们可以用一个生成器函数简写。注意这里的contextmanager其实就是一个函数，它接收我们写的生成器函数，然后返回一个真正支持 with 的对象：

@contextmanager
def xxx():
    # __enter__ 部分
    yield
    # __exit__ 部分

因此你可以简单理解为：@contextmanager把一个包含 yield 的生成器函数，包装成了一个可以被 with 使用的上下文管理器。但是这里的 yield 和普通的生成器有点不太一样，这里主要利用了它的暂停特性，没有用 yield 返回任何值（yield 就等于 yield None），所以我们timer的返回值标记成 Iterator[None]。

有了这些特性，with 可以把资源的获取和释放放在同一个词法范围内，即使发生异常，也会执行清理逻辑。比如举个例子，下面是关于利用锁的两种做法：

# 错误的用锁
lock.acquire()
modify_shared_data()  # 如果报错，则在这里退出
lock.release()

# 正确的用锁，保证了一定能够释放锁的资源，不管 modify_shared_data() 是否报错
with lock:
    modify_shared_data()

# 上面的正确用法相当于
lock.acquire()

try:
    modify_shared_data() # 即使报错了，后面 lock.release() 也会执行
finally:
    lock.release()

另外要注意一件事，就是这个锁资源的行为lock.acquire()要在try外面，因为如果在try里面，假设锁资源的操作出现了问题报错，我们会去进行finally的操作，试图去 release 一个根本没有锁的资源，会报错。反之，如果在外面的话，假设锁资源的操作出现了问题报错，程序会直接抛出异常，也不会进入对应的 finally。

所以我们资源管理的一种通用原则是：先成功获取资源，再进入 try；finally 负责释放已经确定获取成功的资源。

文件（with open(...) as f:）、锁（with lock:）、数据库连接（with connection:）、临时目录、自动混合精度上下文都适合这种模式。它和 C++ 的 RAII 解决的是同一个问题：资源生命周期必须有清晰边界。

2.8 异常处理：只捕获能够处理的错误
# 

# 接收一个字符串 raw，目标是把它转换成一个大于 0 的整数
def parse_world_size(raw: str) -> int:
    try:
        world_size = int(raw)
    except ValueError as exc:
        raise ValueError(f"WORLD_SIZE 必须是整数，实际为 {raw!r}") from exc

    if world_size <= 0:
        raise ValueError("WORLD_SIZE 必须大于 0")
    return world_size

这里的raise可以理解成主动宣布：“这里发生错误，不能继续正常执行了。”而上面代码的raise ... from exc其实发生了两个异常，第一个是int("abc")，产生ValueError: invalid literal for int() with base 10: 'abc'，然后我们捕获它：except ValueError as exc:。接着又主动创建了第二个异常ValueError("WORLD_SIZE 必须是整数...")

from exc 的意思就是：保留原始异常，并明确告诉 Python：新异常是由这个异常引起的。因此构筑起了异常链，能够同时保留两层信息。

建议遵循三条原则：

  1. 捕获具体异常，不要用空的 except: ，因为这样的范围太大，还甚至可能吞掉 KeyboardInterrupt 等信号。核心思想是我知道我准备处理什么错误，才去捕获它。
  2. 只有在能恢复、补充上下文或转换抽象层时才捕获；
  3. 用 raise ... from exc 保留根因链。用它来把一个底层概念转变为上层概念，这就是所谓的“转换抽象层”。

不要把异常用于正常的高频控制流，尤其是在性能敏感循环中。异常应该主要表达异常情况，不要把它当作普通的 if 用。

2.9 类型标注与数据类
#

类型标注主要服务于静态检查、IDE 和读者，不会自动在运行时验证类型。比如假设我们有一个这样的函数：

def add(a: int, b: int) -> int:
    return a + b

a: int 不是意味着 Python 会强制要求 a 是 int！反而，你甚至可以add("hello", "world")，照样可以得到结果 helloworld。所以在这里的a: int，更接近于声明：“我希望这里传进来的是 int”。

同时对于下面的代码来说，我们也可以乱传数据进去，Python 默认不会因为你违反了类型标注就立刻阻止你，它仍然会尝试执行函数内部代码，当然实际能不能执行就另当别论了。

from dataclasses import dataclass
from collections.abc import Sequence

@dataclass(frozen=True) # 自动帮你生成__init__、__repr__ 等，frozen=True 表示创建以后不要修改它
class ShardSpec: # 一个专门用来装数据的类
    rank: int
    world_size: int

def shard(values: Sequence[int], spec: ShardSpec) -> Sequence[int]:
    return values[spec.rank::spec.world_size]

注意这里的Sequence[int]，表示一个“整数序列”。它需要的是能像“序列”一样被下标和切片。比如 list，tuple 都属于Sequence。

常用选择：

  • 参数只要求“可迭代”或“序列”能力时，标注 Iterable[T]、Sequence[T] 等抽象协议，也就是只要求自己真正需要的能力。避免把接口限制的太死；
  • 返回具体容器时可标注 list[T]、dict[K, V]；
  • T | None 表示值可能缺失；
  • Protocol 可描述结构化接口，减少不必要的继承。也就是它描述的是“你需要长成什么样”，而不是“你必须继承谁”；
  • dataclass 适合主要承载数据、规则简单的对象。

类型系统的目标是尽早暴露接口误用，不是把动态语言硬写成 Java。公共边界（接口边界）优先标清，局部显而易见的变量不必逐个标注。

Protocol 和鸭子类型
#

鸭子类型（Duck Typing）： 不关心一个对象具体属于什么类，只关心它是否拥有我需要的方法或能力。

例如：

def make_sound(x):
    x.speak()

这里并不要求 x 必须继承某个 Animal 类，只要它有 speak() 方法即可。

Protocol： 用于把“对象需要具备哪些能力”正式写成类型接口，让 IDE 和静态类型检查器也能理解鸭子类型。

from typing import Protocol

class Speaker(Protocol):
    def speak(self) -> None:
        ...

def make_sound(x: Speaker) -> None:
    x.speak()

一个类即使没有继承 Speaker：

class Dog:
    def speak(self) -> None:
        print("汪")

因为 Dog 具有 speak() -> None 这个结构，所以可以被当作 Speaker 使用：

make_sound(Dog())

鸭子类型是“有这个能力就能用”，Protocol 是把这种能力要求正式写给类型检查器看。

3. Python 并发与性能分析
#

3.1 先分清并发与并行
#

  • 并发（concurrency）：多个任务在同一时间段内推进，同一时刻不一定真的有多个任务在执行，可能只是 CPU 在不同任务之间快速切换。
  • 并行（parallelism）：多个任务在同一时刻真正执行。通常需要多个 CPU 核心、多个进程，或者 GPU 等硬件支持。

不要一看到“任务很多”就想着开线程。先看任务到底是在“等”，还是在“算”。因为不同瓶颈，对应的并发方式完全不同。

选择并发模型前，先判断瓶颈：

任务类型 典型例子 常见选择
I/O 密集 请求服务、读取大量小文件 线程（threading）或 asyncio
Python CPU 密集 纯 Python 解析、复杂循环 多进程（multiprocessing）或原生扩展
原生算子密集 NumPy/PyTorch/CUDA 运算 由底层线程池/GPU 并行，Python 负责调度
大数据跨进程 数据加载、共享缓存 多进程 + 共享内存，避免频繁序列化大对象

针对I/O 密集任务，我们非常适合使用线程（threading）或 asyncio，核心思想都是某个任务等待 I/O 时，让别的任务运行。那么为什么Python 线程适合 I/O？这就需要我们了解下一章的GIL。

针对CPU 密集型任务，多进程可以处理是因为每个进程有自己的 Python Interpreter，也有自己的 GIL，所以可以真正并行。

针对原生算子密集任务，比如用到了NumPy / PyTorch / CUDA，虽然是通过 Python 代码发起的，但真正耗时的计算通常不是由 Python 自己完成，而是交给底层的 C/C++、BLAS、CUDA 等原生实现执行。

针对大数据跨进程任务，要了解不同进程默认拥有彼此独立的内存空间。一个进程里的大对象，不能像多线程那样直接被另一个进程随便访问。因此如果把一个很大的 data 交给多个进程处理，最直接的做法可能会导致数据在进程之间被复制，这会导致：

  1. 内存占用很高
  2. 进程之间传输数据很慢 因此，对于大数据，多进程场景下常考虑使用共享内存（多个进程共同访问同一块内存，而不是每个进程都复制一整份数据）

进程之间传递普通 Python 对象时，通常不能直接传内存中的对象本身，而是需要先把对象转换成可以传输的形式。这个过程就叫做序列化（serialization）。所以在大量数据跨进程时，显然就要尽量减少数据复制和序列化，尽量使用共享内存。

解释一下大数据跨进程中的两个常见例子：

  1. 数据加载：多个 worker 进程并行读取/预处理数据，再把 batch 交给主进程；如果数据很大，跨进程复制和序列化会有明显开销。
  2. 共享缓存：多个进程都要访问同一份大数据时，使用共享缓存/共享内存可以避免每个进程各复制一份。

3.2 GIL 到底限制了什么
#

常见 CPython 构建使用全局解释器锁（GIL）保护解释器内部状态。一个进程里的多个 Python 线程，要执行 Python 字节码时，需要先拿到 GIL。因此在同一进程中，通常只有一个线程能同时执行 Python 字节码。也意味着两个执行纯 Python CPU 循环的线程一般不能获得两倍速度。所以纯 Python CPU 密集型任务，一般不靠多线程来实现多核并行，这个场景更典型的是使用多进程。

但这不等于“Python 线程没有用”，GIL 限制的是执行 Python 字节码，并不代表线程任何时候都必须占着 GIL：

  • 阻塞 I/O 时解释器会释放 GIL；
  • NumPy、PyTorch 等原生扩展可在耗时计算时释放 GIL；
  • 后台日志、预取和轻量控制任务常适合线程。

GIL 是 CPython 实现细节，不应泛化成所有 Python 实现或所有构建的永恒规则。判断性能时要测量当前解释器和依赖，而不是只背结论。

3.3 线程：共享内存，也共享风险
# 

from concurrent.futures import ThreadPoolExecutor
from urllib.request import urlopen

# 访问这个url，等待服务器响应后，返回响应内容有多少字节
def fetch_size(url: str) -> int:
    with urlopen(url, timeout=10) as response:
        return len(response.read()) # 先在try里面先完成len(response.read())，然后一直做完上下文管理器的finally后，return 完成的len(response.read())

urls = ["https://example.com"] * 4

# 不使用线程的做法
sizes = []
for url in urls:
    sizes.append(fetch_size(url)) # 串行的执行这个函数，很多时间都浪费在等待网络

# 使用线程池以后（这里创建了一个线程池，最多同时使用4个工作线程）
with ThreadPoolExecutor(max_workers=4) as pool:
    sizes = list(pool.map(fetch_size, urls))

注意这里的urlopen(...)和response.read()都可能发生网络等待，所以这种任务就是典型的 I/O 密集型任务。

代码中的pool.map(fetch_size, urls)，概念上很像map(fetch_size, urls)，区别是普通map基本上是依次执行，而pool.map(...)会把这些任务交给线程池并发执行。

pool.map(fetch_size, urls)其含义相当于让四个线程分别执行：

线程1：fetch_size(url1)
线程2：fetch_size(url2)
线程3：fetch_size(url3)
线程4：fetch_size(url4)

它们可以一起等待网络，理想情况下和只去访问一个url的时间差不多。

我们还要注意，线程共享进程内存，传数据便宜，但对同一可变对象的“读取—修改—写回”可能产生竞态导致错误，我们要使用锁：

from threading import Lock

lock = Lock() # 锁
counter = 0

def increment() -> None:
    global counter
    with lock:
        counter += 1

这里的with lock:等于：

lock.acquire()

try:
    counter += 1
finally:
    lock.release()

确保了同一时刻只有一个线程能够执行counter += 1，所以最终结果一定正确。

同时我们还需要锁时让临界区（被锁保护的这一小段，在上面的代码中就是counter += 1）尽可能小，也就是只锁真正需要保护的共享数据操作。

原子操作指的是执行过程中不能被拆开、不能做到一半被别的线程插进来的操作。不要依赖“某个内置操作看起来是原子的”来设计正确性；解释器版本、对象实现或复合操作都可能破坏这种假设。而且更常见的问题是：即使单独几个操作各自安全，组合起来也不安全。

因此我们判断是不是需要同步，应该看整个“读取 → 判断 → 修改”逻辑，而不是只看一条python语句。

3.4 多进程：绕开 GIL，但数据搬运有成本
# 

from concurrent.futures import ProcessPoolExecutor

# 判断素数，属于典型的 CPU 密集型任务
def count_primes(limit: int) -> int:
    def is_prime(value: int) -> bool:
        if value < 2:
            return False
        return all(value % divisor for divisor in range(2, int(value**0.5) + 1))
    return sum(is_prime(value) for value in range(limit))

if __name__ == "__main__":
    # 启动多个进程，让 4 个进程分别执行一次 count_primes(50000)
    with ProcessPoolExecutor() as pool:
        results = list(pool.map(count_primes, [50_000] * 4))

使用多进程时，把“创建子进程”的代码放在if __name__ == "__main__":中。因为 spawn 创建的子进程会重新导入当前模块，如果创建进程的代码位于模块顶层，子进程导入时可能再次创建子进程，导致递归创建。来看个例子，如果我们把上面的代码这么写：

from concurrent.futures import ProcessPoolExecutor

def count_primes(...):
    ...

with ProcessPoolExecutor() as pool:
    ...

我们的主导入 demo.py（假设文件名叫这个），他会创建子进程，然后我们的子进程会重新导入当前模块demo.py，然后又看到了with ProcessPoolExecutor() as pool:，子进程又去创建自己的子进程…

但是加上if __name__ == "__main__":以后，只有主进程直接运行文件时__name__ == "__main__"。使用 spawn 创建子进程重新导入这个模块时，这个模块是被导入的模块，不是程序入口，因此通常是__name__ = "__mp_main__"，我们的判断不成立，所以不会继续去创建。

顺便区分一个容易混淆的情况：普通 import 时，name 通常就是模块名。也就是哪个文件被直接运行，哪个文件的 name 就是 “main"；被 import 的模块，name 通常就是它的模块名。

多进程的主要成本包括：

  • 创建进程和独立解释器；
  • 参数与返回值的序列化/反序列化，进程间常常需要pickle序列化/反序列化传递普通 Python 对象；
  • 复制或映射内存；
  • 进程间通信与同步。

核心就是进程之间不像线程那样天然共享同一个 Python 内存空间。

如果每个任务只做几十微秒工作，调度成本可能比计算更高。应增大任务粒度，也就是一次分配出去更多工作，让“实际计算时间”远大于“调度和通信时间”，并尽量避免来回传递大型数组或张量。

GPU 关联：CUDA 不是普通的 Python 内存状态，父进程已经初始化 CUDA 以后，再用fork复制出子进程，子进程拿到的CUDA状态可能是不完整或不安全的。因此不要在父进程初始化CUDA后随意 fork。

3.5 asyncio：协作式 I/O 并发
#

简单来说，asyncio 通常是在一个线程里的事件循环中，让很多任务轮流推进，而 await 就是任务主动说“我现在要等东西，你先去跑别人吧”。

import asyncio

async def worker(name: str, delay: float) -> str: # 定义了一个协程函数
    # 一个异步等待函数，当前协程暂停，线程没有被阻塞
    await asyncio.sleep(delay)  # 模拟异步非阻塞 I/O
    return name

async def main() -> None:
    # asyncio.gather()是把这两个协程都安排起来，并发执行，然后等它们全部结束
    # 并且要注意它的结果顺序按照传入顺序，不按照完成顺序。
    results = await asyncio.gather(
        worker("a", 0.2), # 并不会像普通函数那样立刻完整执行，而是得到一个协程对象，之后交给事件循环调度
        worker("b", 0.1),
    )
    print(results)

# 创建一个事件循环，然后把 main() 扔进去，一直运行，直到 main 完成，最后关闭事件循环
asyncio.run(main())

asyncio 用事件循环调度协程（coroutine）。事件循环，你可以想象为一个调度员，它不断判断现在哪个协程可以继续执行。例如 worker a 现在执行到await asyncio.sleep(0.2)，事件循环就会去运行 worker b。

还有重要的一点，就是协程只会在 await 处主动让出控制权。如果一个 async def 的函数里面没有 await，那么一旦事件循环开始执行它，它基本会连续全部执行完，不会莫名其妙执行到某一行代码时突然切换到另一个协程。因此 asyncio 属于一种协作式调度，而不是线程那种操作系统可以在任意时刻抢占执行权的模型。await 只能写在 async def 中。

由于asyncio，让上面的代码中的两次 asyncio.sleep 可以重叠，所以总体大约只需要 0.2 秒左右，这正是 asyncio 特别适合 I/O 密集任务 的原因。

在事件循环中直接执行阻塞 I/O （比如 time.sleep(10) 就是一个阻塞操作，注意它没写await）或长时间 CPU 计算会卡住所有协程。而事件循环通常运行在一个线程里。只要这个线程被阻塞，其他协程就没法调度。

此时应改用异步库，或把阻塞工作放到线程/进程执行器。

另外，对于await我们还要明白: await 一个 CPU 密集协程，如果这个协程内部没有 await，它仍然会一直执行到结束，不会中途切换到其他协程。比如这个例子：

async def fun():
    total = 0
    for i in range(1_000_000):
        total += i
    return total

async def main():
    result = await fun()

因为 fun() 内部没有暂停点，它会从头跑到尾。

另外要知道，await xxx 会先进入/推进 xxx 的执行，直到 xxx 自己遇到一个真正需要等待、需要挂起的点，才把控制权交回事件循环。

3.6 正确做基准测试
#

性能测试不能“随便掐一次表”，而要尽量测到稳定、真实、可重复的执行时间。性能测试最常见的错误是只测一次、把初始化算进去，或者忘记 GPU 异步执行。

如果我们只去这样运行一次函数：

start = perf_counter()
fn()
end = perf_counter()

得到 12.8ms，这个数字只能说明：这一次，在当前机器状态、当前 CPU 调度、当前缓存状态下，它花了 12.8ms。所以 benchmark 的目标不是得到一个数字，而是设计一个尽量公平的实验，让这个数字具有代表性。另外，我们要明确我们现在要去测量什么东西，然后把性能测试的边界画准确。

纯 CPU 小片段可用 timeit：

python -m timeit -s 'xs = list(range(1000))' 'sum(xs)'

这里-s 'xs = list(range(1000))'，也就是先运行xs = list(range(1000))。然后真正被benchmark的只有sum(xs)。 所以所以 timeit 帮你自动区分“准备数据”和“我要测的代码”。

对于一个特别短的代码，操作系统调度的一个轻微抖动甚至可能比代码本身还要对总耗时的影响还要大，所以对于特别短的代码，正确策略不是测一次，而是测很多次，计算平均时间。timeit 就是专门帮你做这件事的。所以 timeit 特别适合微基准测试（microbenchmark）。

手工测试至少要做到：

from statistics import median
from time import perf_counter

def benchmark(fn, warmup: int = 5, repeat: int = 20) -> float:
    # 先进行warmup，这几次运行不计时。因为第一次执行经常与后面的执行不一样。
    # warmup 是为了让系统进入稳定态
    for _ in range(warmup):
        fn()

    samples = []
    for _ in range(repeat):
        start = perf_counter() # perf_counter()是专门设计来测时间间隔的高精度计时器。perf_counter() 的重点是“差值”，不是绝对值。
        fn()
        samples.append(perf_counter() - start)
    return median(samples) # median选取中位数，因为平均数很容易受到一次偶发系统抖动影响

对于 GPU，Kernel 启动通常是异步的。GPU异步启动指的是CPU 和 GPU 可以重叠工作。而CPU 计时器只量到“提交任务”的时间，而任务可能GPU还在做，还没有完成，这样的话我们的计时就有问题。比如下面的代码，可能我们 CPU 提交任务花了0.1 ms，GPU 真正计算花了5 ms，这样的话我们计算得到的 elapsed 只有 0.1ms，这显然有问题：

start = perf_counter()
y = torch.matmul(a, b)
elapsed = perf_counter() - start

因此我们需要在边界同步，比如下面的常见的 pytorch CUDA 写法：

torch.cuda.synchronize() # 确保测试开始之前，GPU 前面的旧任务全部做完
start = perf_counter()

y = torch.matmul(a, b)

torch.cuda.synchronize() # 确保刚才这个任务真的执行完，再停止 CPU 计时器。
elapsed = perf_counter() - start

注意我们要在开始前也写torch.cuda.synchronize()，因为有可能GPU 在 start 之前还有一个旧任务没做完。那么计时结果就变成 “旧任务残留时间 + 新任务时间”。

另一种方法是使用框架提供的 GPU Event。因为perf_counter()本质上还是 CPU 时钟，而 GPU 有自己的执行时间线，所以很多框架提供在在 GPU 流里面直接插入“时间戳”。思想就是：CPU timer 看 CPU 时间线；GPU Event 看 GPU 时间线。

同步会改变流水线行为，本来的流水线会因为计时产生停顿。因此端到端吞吐 throughput（比如：整个模型每秒能处理多少张图片？）和单算子延迟 latency（比如：一个矩阵乘法实际花多少时间？）应分别测量。

3.7 从“慢”定位到具体代码
#

建议按由粗到细的顺序：

  1. 端到端计时：也就是查看程序整体的执行耗时，确认性能回归（也就是比之前执行的慢）真实存在；

  2. 阶段计时：区分数据、计算、通信和保存，找出是哪一个大阶段出了问题；

    python -m cProfile -o profile.out train.py # 用 cProfile 运行整个 train.py，并把 profiling 结果保存到 profile.out
python -m pstats profile.out # 进入结果查看工具

  3. 函数级 profiling：用 cProfile 找累计耗时高的函数； 在 pstats 中可按累计时间排序：

    sort cumulative
stats 30

    cProfile 记录每个 Python 函数被调用多少次，以及它们花了多少时间。一个比较常见的输出列大概是：

    项目 说明
    ncalls 函数被调用的次数。
    tottime 函数自身消耗的总时间，不包括它调用的其他函数。
    percall tottime / ncalls，函数每次调用平均自身耗时。
    cumtime 函数自身 + 它调用的所有子函数的累计耗时。
    percall cumtime / 原始调用次数，每次调用平均累计耗时。
    filename:lineno(function) 函数所在的文件名、定义行号以及函数名。

    cProfile 中的 cumtime 就是这个函数本身 + 它调用的所有下层函数，总共消耗了多少时间。通过 python -m cProfile -s cumulative demo.py 我们让 cProfile 中 cumtime 的结果按照累计时间排序，适合用它找哪个函数树占用了最多运行时间。

    tottime就是函数自身执行的时间。不包括它调用其他函数的时间。python -m cProfile -s time demo.py是让我们的结果按照 cProfile 中 tottime 进行排序。

  4. 行级/采样 profiling：进一步定位热点行或原生调用栈，采样profiling类似于：每隔一小段时间，看一下“程序现在正在执行哪里”；

  5. 内存 profiling：程序性能问题不只有 CPU 慢，内存泄漏和不必要的数据保留也是问题。我们可以用 tracemalloc 等工具找 Python 分配增长； 一个检查 Python 内存分配的例子：

    import tracemalloc
# 开始跟踪python的内存分配
tracemalloc.start()

# 运行待检查代码
...

# 取得目前内存分配情况的快照
snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics("lineno")[:10]:
    print(stat)

    但是要注意tracemalloc主要追踪Python 自己管理的内存分配。如果显存主要是 CUDA / PyTorch 底层分配，就不能指望上tracemalloc，应该用下一步的操作。

  6. GPU profiling：如果发现真正慢的是PyTorch/CUDA，普通 cProfile 就不够用了。我们可以进入 PyTorch Profiler、Nsight Systems/Compute 等专用工具。 这几种工具中，PyTorch Profiler 是从 PyTorch 角度看 operator/kernel 时间；Nsight Systems 是看整个 CPU + CUDA 时间线；Nsight Compute 是深入研究某一个 CUDA kernel 为什么慢。

性能优化一定要“由粗到细”，因为核心思路就是：先找热点，再优化热点。

3.8 Python 性能优化的优先级
#

推荐顺序如下：

  1. 先改算法复杂度和数据结构；

  2. 减少不必要的 I/O、复制和序列化；

  3. 把细粒度 Python 循环改成批处理/向量化原生算子； 比如在矩阵运算用 Numpy，相比于原生python可以极大提升速度。

  4. 减少 Python 与 C++/GPU 边界的频繁往返； 例如，一百万次小算子调用即使每次都很快，也会累积大量调度开销（不是实际计算本身产生的时间，而是为了“发起这次计算”所花的额外时间）。把数据组成批次后调用一次大算子，通常比微调 Python 语法有效得多。

  5. 确认热点后，再写 C++、CUDA 或 Triton 扩展。

Python 性能优化应优先减少计算量、数据搬运和 Python 层调用次数；先通过算法优化和批处理把工作交给高效的原生算子，只有在 profiling 确认热点且现有算子仍不足时，才考虑 C++/CUDA/Triton 扩展。
