4. C/C++：内存、生命周期与资源管理
#

4.1 值、地址、指针与引用
# 

#include <iostream>

int main() {
    int value = 42;
    int* ptr = &value;  // ptr 保存 value 的地址
    int& ref = value;   // ref 是 value 的别名

    *ptr = 7;           // 解引用指针并写入
    ref += 1;

    std::cout << value << '\n';  // 8
}

注意要区分一个容易混淆的点，当 & 出现在表达式里：&x，表示取 x 的地址；如果 & 出现在“类型声明”里，如int& ref = x，则表示ref 是一个 int 的引用。

可以先用这张表建立直觉：

概念 能否为空 能否改指向 常见用途
值 T 否 不适用 拥有一个独立对象
指针 T* 可以是 nullptr 可以 可选对象、数组、底层接口、非拥有观察
引用 T& 语言语义上必须绑定对象 不可以重新绑定 必须存在的别名、常用于函数参数
常量引用 const T& 必须绑定对象 不可以 避免复制且不允许修改

对于const T&，可以理解为给原对象起一个“只读别名”。我们可以用过 ref 读取，但是不能通过 ref 修改。

函数参数表达的接口意图应尽可能清晰。函数参数类型本身就在告诉调用者：这个函数准备怎么对待你的对象。

void consume(T value);          // 复制一份传进来的值，修改它不会影响外面
void update(T& value);          // 直接操作外面的原对象，可以修改它
void inspect(const T& value);   // 直接读取原对象，不复制，也不能修改
void optional(T* value);        // 传对象地址，也可以传 nullptr

对小型标量（int、float、指针）按值传递通常最清楚；不要机械地把所有参数都改成引用。不是“引用能避免复制”，就应该把所有函数参数都写成引用。

4.2 数组、指针与连续内存
#

原生数组在大多数表达式中会退化为首元素指针，因此单独的 T* 不携带长度：

void scale(float* data, std::size_t size, float factor) {
    for (std::size_t i = 0; i < size; ++i) {
        data[i] *= factor;
    }
}

如果使用上面这个函数，C/C++ 的原生数组传给函数时，通常只会变成“指向第一个元素的指针”，数组长度不会一起传过去。比如调用scale(arr, 4, 2.0f);，传入的arr相当于传成&arr[0]，因此我们只知道数据从哪里开始，而不知道一共有多少个元素。所以函数必须额外传一个std::size_t size告诉它长度。

std::size_t：C++ 中专门用于表示对象大小、元素数量和下标的非负整数类型（≥0）。

而在现代 C++ 中优先用能表达长度的类型：

#include <span>

void scale(std::span<float> values, float factor) {
    for (float& value : values) {
        value *= factor;
    }
}

std::span<T>：对一段连续 T 数据的非拥有视图，可理解为“指针 + 长度”；它不复制、不管理数据，因此底层数据在使用 span 期间必须保持有效。

比如对于一个std::span<int> values，我们可以使用values[i]和values.size()

二维矩阵通常线性存放。行主序（C/C++ 的二维原生数组采用行主序：先存完第 0 行，再存第 1 行，再存第 2 行）矩阵 A[M][N] 的 (row, col) 对应偏移。这意味着你看到的是二维矩阵，但计算机内存本质上是一条一维的连续空间：

$$ \text{offset} = row \times N + col $$

这个公式会在 CUDA 中反复出现。访问顺序是否连续，直接影响 CPU cache 和 GPU 合并访存效率。按内存真正的排列顺序访问，通常会更快。

比如对于一个矩阵：

A00 A01 A02 A03
A10 A11 A12 A13
A20 A21 A22 A23

如果我们遍历的顺序是：

// 访问顺序：A00 → A01 → A02 → A03 → A10 → A11 → ...
for (int row = 0; row < M; ++row) {
    for (int col = 0; col < N; ++col) {
        use(A[row][col]);
    }
}

这样的遍历顺序和内存排列完全一致，这就是连续访问。这对于CPU很友好，因为 CPU 读取一个元素时，通常会顺便把附近的一块数据装入CPU cache。而对于GPU来说，CUDA 中有很多线程，如果相邻线程访问相邻地址还有利于合并访存（把访问合并成较少的内存事务），效率很高。

4.3 对象存储期与生命周期
#

常见存储位置的说法是“栈”和“堆”，但更准确地应关注对象的存储期和所有权，也就是说更重要的是搞清楚：这个对象什么时候创建、什么时候销毁，以及谁负责销毁它：

void example() {
    int local = 1;                  // local 是一个局部变量。执行到变量声明时被创建，函数结束、离开作用域时，它会自动销毁

    //new T[...] 创建动态数组，并返回数组首元素的地址，因此返回类型是 T*；所以接收它的变量自然是指针
    auto buffer = new float[1024];  // 这块内存是在程序运行过程中，通过 new 主动申请出来的（动态分配）
    delete[] buffer; // 手动删除
}

在上面的代码中。buffer 本身只是一个指针变量 float* buffer，它是局部变量，所以 buffer 自己会在函数结束时自动消失，但是new float[1024]创建出来的那块内存不会因为函数结束自动释放。因此必须要delete[] buffer来手动销毁这个动态对象，如果我们不在 example 内销毁的话，函数结束之后 buffer 被销毁，指针没了，但是float[1024]还在，但是却再也找不到它，这就是内存泄漏。

手工 new/delete 容易产生：

  • 内存泄漏：忘记释放； 就比如上面的操作如果不写delete[] buffer就会导致内存泄漏。

  • 重复释放：同一地址释放两次； 比如把同一个内存释放两次：

    float* p = new float[100];

delete[] p;
delete[] p;   // 错误

  • 悬空指针：对象已销毁，指针仍被使用； 例如：

    float* p = new float[100];
delete[] p;

p[0] = 1.0f;   // 错误

  • 分配/释放形式不匹配：new[] 配了 delete； 注意在cpp中，数组分配必须对应数组释放，也就是 new T 对应 delete，而 new T[] 对应 delete[]

  • 异常路径泄漏：释放前函数提前退出。也就是本来打算在函数最后 delete，但函数中途因为异常或提前 return 离开了，于是 delete 根本没执行。

因此现代 C++ 的默认原则是：**让资源由对象管理，让对象由作用域管理。**现代 C++ 关注“谁拥有对象、对象何时销毁”：局部对象由作用域自动管理；动态资源应交给 vector、string、unique_ptr 等 RAII 对象管理，尽量避免直接使用 new/delete。

比如下面这个例子：

// 曾经的做法
void example() {
    float* buffer = new float[1024];
    delete[] buffer; // 手动销毁
}

//现代C++更推荐：
void example() {
    std::vector<float> buffer(1024);// 使用 buffer
} // 离开函数时自动释放

4.4 RAII：把资源绑定到对象生命周期
#

RAII（Resource Acquisition Is Initialization）在构造时获取资源，在析构时释放资源。也就是把“资源的释放”绑定到一个 C++ 对象（根据某个类型/类实际创建出来的一个具体实例）的生命周期上，这样对象销毁时，资源就自动释放。

#include <cstdio>
#include <stdexcept>

// 定义了一个叫 File 的类型，它专门负责“打开一个文件，并在自己销毁时把文件关掉”
class File {
public:
    explicit File(const char* path) // 构造函数
        : handle_(std::fopen(path, "rb")) {
        if (handle_ == nullptr) {
            throw std::runtime_error("failed to open file");
        }
    }

    // 析构函数，对象被销毁的时候，C++ 自动调用这个函数！
    ~File() {
        std::fclose(handle_); // 关闭文件
    }

    // 禁止复制 File 对象
    File(const File&) = delete;
    File& operator=(const File&) = delete;

// 下面的变量只能在 File 类内部使用，外面不能随便访问
// 也就是对象内部保存的资源
private:
    std::FILE* handle_;
};

函数正常离开作用域，或者因为异常进行栈展开时，已经成功构造完成的局部对象都会被析构。 但如果某个对象自己的构造函数抛出异常，那么这个对象本身还没有构造完成，因此不会调用它自己的析构函数；已经构造完成的成员和基类会被正确析构。

但是要注意，如果一个对象构造失败时，C++ 会自动销毁在这次构造过程中已经成功构造完成的子对象，包括成员对象和基类对象。举一个例子：

class A {
public:
    A()// 构造函数名
        // 成员初始化列表
        : b_(), //调用B 的默认构造函数
          c_(),
          d_()
    // 构造函数的函数体
    {
        // A 的所有成员都已经构造成功
        throw std::runtime_error("A 构造过程中发生错误");
    }

private:
    // 声明 A 有这些成员
    // 成员真正的构造顺序，是按照成员声明顺序，而不是初始化列表里写的顺序
    B b_;
    C c_;
    D d_;
};

int main() {
    try {
        A a;
    }
    catch (const std::exception& e) {
        std::cout << "捕获异常：" << e.what() << '\n';
    }
}

在这里，我们假设成员初始化可以正常进行，B C D 都可以正常构造初始化。我们进入到 A 的构造函数后会发生异常的话，具体执行流程大概是： B 构造 --> C 构造 --> D 构造 --> 进入 A 构造函数主体 --> throw --> D 析构 --> C 析构 --> B 析构 --> catch成功，输出"捕获异常：A 构造过程中发生错误"

注意，没有 A 析构！因为 A 自己还没有构造完成。

但是如果析构函数自己抛异常，就会导致释放资源失败。析构函数原则上不应该让异常逃出去。

另外在构造函数里就应该对所有资源初始化，比如类A有一个成员变量类B，A的构造函数需要初始化类B。

另外来看这个情况：

{
    A* pa = new A();
} // 退出一个 {} 块

这个时候就算 A 是RAII的类，但是我们是通过 new 构造的对象，对于这个对象，我们析构的时机是delete，什么时候 delete 什么时候才析构。

文件、锁、主机内存、GPU 内存、CUDA Stream 都可以用同一思想管理。

实际项目中优先使用标准库已有的 RAII 类型，如 std::vector、std::string、std::fstream、std::lock_guard 和智能指针，不要重复造轮子。

4.5 智能指针与所有权
# 

#include <memory>

auto unique = std::make_unique<Buffer>(1024);  // 唯一所有权
auto shared = std::make_shared<Buffer>(1024);  // 共享所有权
类型 语义 成本与注意点
std::unique_ptr<T> 唯一拥有，可移动不可复制 成本接近裸指针，默认首选。unique 被销毁，Buffer 也自动释放
std::shared_ptr<T> 引用计数共享拥有 最后一个 shared_ptr 消失的时候自动会释放 Buffer。因此 shared_ptr 内部会维护一个引用计数，有计数与控制块成本，循环引用需 weak_ptr
std::weak_ptr<T> 不增加引用计数的观察者 因为 weak_ptr 不拥有对象，所以你观察的对象可能已经没了。所以使用前要 lock() 检查对象是否仍存在
T* / T& 通常表示非拥有访问，不负责管理它的生命周期 被指向对象必须活得足够久

如果所有权没有共享需求，不要使用 shared_ptr。“避免思考所有权”不是共享所有权的合理理由。

C++ 对象的拷贝与移动
#

因为程序里面经常要把一个对象的数据交给另一个对象。但是这个“交给”有两种完全不同的需求：

  1. 希望保留原对象并得到一份独立副本 → 拷贝
  2. 当原对象不再需要、只想高效地把内部资源交给另一个对象 → 移动

而根据接收对象是新建还是已经存在，又分别产生拷贝构造、移动构造、拷贝赋值和移动赋值。

总体来看是这样的：

我要做什么 新对象 已存在对象
复制 拷贝构造 拷贝赋值
转移资源 移动构造 移动赋值

拷贝构造
#

用一个已经存在的对象，创建一个新的同类型对象。

#include <iostream>
#include <string>

// 类定义
class Person {
public:
    std::string name;
    int age;
};

// 对象a
Person a;
a.name = "Tom";
a.age = 20;

// 对象b
// 注意 b 是一个全新的对象，使用了拷贝构造
Person b = a;

// 另外几种拷贝构造形态
Person c(a);       // 同样是用 a 创建新对象 c

void foo(Person p); // 按值传参，也会拷贝构造参数 p
foo(a);

// 从结果来看会有
// a.name = "Tom"
// a.age  = 20

// b.name = "Tom"
// b.age  = 20

注意这里的 b 是一个全新的对象。之后如果b.age = 30;，不会把a.age变成30。

拷贝构造函数具体如下：

class Person {
public:
    // Person 的拷贝构造函数
    // 意思是 给我一个已经存在的 Person -> 根据它构造一个新的 Person
    Person(const Person& other)
        : name(other.name),
        age(other.age) {
    }

private:
    std::string name;
    int age;
};

注意这里的参数用的是const Person&，因为我们只是读取原对象，不想修改它。

如果我们不写拷贝构造，很多情况下编译器会自动生成。对普通成员来说，这通常没问题；但是真正麻烦的是裸指针。来看一个这个情况：

class Buffer {
public:
    Buffer(int size) {
        data = new int[size];
    }

private:
    int* data;
};

Buffer a(100);
Buffer b = a;

如果我们什么都不写，编译器默认会把成员 data 的值复制过去，但是在这里 data 是一个指针。这样的话 a.data 和 b.data 相同，这两个对象指向了同一块内存，这就是浅拷贝，很危险。

因为如果这个类的析构函数不写delete[] data的话，这块 new 出来的内存会泄露。

如果这个类写了一个负责delete[] data的析构函数，销毁 a 和 b 的话，会导致同一块内存释放两次，因此对于自己管理资源的类，默认拷贝往往不够。我们要自己去写深拷贝。

所以可以写：

class Buffer {
public:
    Buffer(int size)
        : size_(size),
          data_(new int[size]) {
    }

    // 拷贝构造函数
    Buffer(const Buffer& other)
        : size_(other.size_), // 复制大小
          data_(new int[other.size_]) //重新去申请一块自己的内存
        {
        // 把内容一个个复制过去
        for (int i = 0; i < size_; ++i) {
            data_[i] = other.data_[i];
        }
    }

    ~Buffer() {
        delete[] data_;
    }

private:
    int size_;
    int* data_;
};

拷贝赋值
#

把一个已经存在的对象的内容，复制给另一个已经存在的同类型对象。要注意和 拷贝构造 进行区分。

拷贝赋值函数大概长成Buffer& operator=(const Buffer& other)，具体一点就是：

class Buffer {
public:
    Buffer& operator=(const Buffer& other) {
        // 把 other 的内容复制给当前对象
        return *this;
    }
};

Buffer a(100);
Buffer b(200);

b = a; // 拷贝赋值，也就是b.operator=(a)

拷贝赋值通常比拷贝构造更加麻烦一点，因为 b 原来可能有自己的资源，所以通常要先处理旧资源，然后再复制，比如看下面这个有资源的情况：

// 一块有内存资源的buffer
class Buffer {
public:
    Buffer(int size)
        : size_(size),
          data_(new int[size]) {
    }

    // 拷贝赋值函数
    Buffer& operator=(const Buffer& other) {
        // 解决了自赋值的特殊情况
        if (this == &other) {
            return *this;
        }

        delete[] data_; // 释放当前对象原来的资源

        size_ = other.size_; // 复制 other 的 size
        data_ = new int[size_]; // 重新申请一块新的内存

        // 把 other 的数据复制过来
        for (int i = 0; i < size_; ++i) {
            data_[i] = other.data_[i];
        }

        // 返回当前对象
        return *this;
    }

    ~Buffer() {
        delete[] data_;
    }

private:
    int size_;
    int* data_;
};

通过上面的操作，我们可以先释放自己原先的资源，然后再复制。同时注意到我们这里的if (this == &other)判断，通过这个方法我们讨论了自赋值（self-assignment）的情况。如果不写，我们的拷贝赋值函数会先把 a 自己的数据删掉，然后又想从已经释放的内存里读，这显然有问题。

这里拷贝赋值函数中的this是一个指针，指向当前对象。所以*this就是这个对象本身。

另外，这里的拷贝赋值函数中返回的是Buffer&而不是void，因为这样可以支持a = b = c;，实际的结合顺序就大概是a = (b = c);。先b = c;然后返回 b 自己，然后a = b;。所以赋值运算符通常返回T&，也就是当前对象的引用。

移动构造
#

如果原对象已经不打算继续使用了，创建新对象时，就不需要把资源完整复制一份。因为既然原对象不需要那些资源了，为什么不直接把资源交给新对象呢？这就是一种移动。

来看一个移动构造的代码：

class Buffer {
public:
    Buffer(int size)
        : size_(size),
          data_(new int[size]) {
    }

    // 移动构造
    // noexcept 表示这个移动构造函数承诺不会抛异常。
    Buffer(Buffer&& other) noexcept
        : size_(other.size_),
          data_(other.data_) // 注意这里是复制指针里面保存的地址。
        {

        other.size_ = 0;
        other.data_ = nullptr; // 把原来的指针清空
    }

    ~Buffer() {
        delete[] data_;
    }

private:
    int size_;
    int* data_;
};

Buffer a(100);
Buffer b = std::move(a); // 调用移动构造

注意，这里要把a.data_设成 nullptr，也就是清空指针。必须取消 other 对原内存的所有权，设置为 nullptr 只是其中一种方式。 因为两个对象最终都会析构。如果我们移动之后不写other.data_ = nullptr;，a和b会在析构函数中释放同一个资源，会 double free 出错，所以我们必须把资源的原拥有者清空。清空以后之后它做 delete[] nullptr; 操作是安全的，什么都不会发生。

接下来解释一下std::move(a)操作，它本身并不会移动任何东西。它是告诉编译器 a 可以被当成一个可以被移动的对象。然后编译器就会选择用移动构造来进行资源转移。

注意，要区分Buffer b = std::move(a)和Buffer b = a;，前者是移动构造，后者是拷贝构造。

移动之后 a 还是一个合法对象，但是它很有可能里面的内容变化了。a 以后还是会正常析构的。

由于移动构造是直接转移资源，而不用申请新资源，通常只需要转移几个内部成员，因此常常非常快，效率非常高。

移动赋值
#

两个对象都已经存在，把右边对象的资源转移给左边对象。

在接管 a 的资源之前，必须妥善处理 b 原有的资源，可以直接释放，也可以通过交换等方式转移。这就是移动赋值和移动构造最大的区别。

来实现一个移动赋值：

class Buffer {
public:
    Buffer(int size)
        : size_(size),
          data_(new int[size]) {
    }

    // 移动赋值
    // noexcept 表示承诺不会抛异常。
    Buffer& operator=(Buffer&& other) noexcept {
      // 防止自己移动给自己
      if (this == &other) {
          return *this;
      }

      // 释放左边（当前对象）原来的资源
      delete[] data_;

      // 接管右边的资源
      data_ = other.data_;
      size_ = other.size_;

      // 把右边的资源清空
      other.data_ = nullptr;
      other.size_ = 0;

      return *this;
    }

    ~Buffer() {
        delete[] data_;
    }

private:
    int size_;
    int* data_;
};

Buffer a(100);
Buffer b(200);

b = std::move(a); // 调用移动赋值

注意这里也一定让原对象不再拥有资源，原因和之前的移动构造一样，防止同样的资源被释放两次。

4.6 拷贝、移动与 Rule of Zero
#

std::vector 等容器拥有资源，复制会复制内容，移动则转移内部资源：

#include <utility>
#include <vector>

std::vector<float> make_buffer() {
    std::vector<float> values(1'000'000, 0.0f);
    return values;  // 编译器通常消除复制，必要时可移动
}

auto a = make_buffer();
auto b = std::move(a);  // a 仍有效，但内容处于未指定状态

如果类只由标准库 RAII 成员组成，通常无需手写析构、复制和移动操作，这就是 Rule of Zero。只有直接管理特殊资源时才需要自定义这些操作，并清晰定义所有权。

不要随手对返回值写 std::move；它可能阻止返回值优化。也不要在移动后假设源对象仍保留原内容。

4.7 const：把不可修改写进接口
# 

const float* p1;        // 指向 const float：不能通过 p1 改值
float* const p2 = ptr;  // const 指针：不能让 p2 改指向
const float* const p3 = ptr;

成员函数末尾的 const 表示不修改对象的可观察状态：

class TensorView {
public:
    std::size_t size() const { return size_; }
private:
    std::size_t size_{};
};

const 有助于编译器和读者验证接口，但不能自动解决并发安全与底层别名问题。

4.8 未定义行为为什么危险
#

越界访问、使用悬空引用、有符号整数溢出、数据竞争等可能触发未定义行为（Undefined Behavior，UB）。编译器可以假设 UB 永不发生，并据此优化；程序结果不一定只是“报错”，也可能在调试版正常、优化版悄悄算错。

std::vector<int> values(4);
values[4] = 1;  // 越界，未定义行为

调试时可启用警告和 Sanitizer：

g++ -std=c++20 -Wall -Wextra -Wpedantic \
    -fsanitize=address,undefined -g main.cpp -o app
./app

AddressSanitizer 常用于发现越界、use-after-free；UndefinedBehaviorSanitizer 检查多类 UB；ThreadSanitizer 可定位数据竞争，但通常不能和 AddressSanitizer 同时启用。

5. C++ 编译、链接、模板与构建系统
#

5.1 从源代码到可执行文件
# 

源文件 .cpp
  └─ 预处理：展开 #include、宏和条件编译
      └─ 编译：语法/类型检查并生成汇编
          └─ 汇编：生成目标文件 .o
              └─ 链接：解析符号并生成可执行文件或库

可以逐步观察：

g++ -E main.cpp -o main.ii       # 只预处理
g++ -S main.ii -o main.s         # 生成汇编
g++ -c main.cpp -o main.o        # 生成目标文件
g++ main.o -o app                # 链接

头文件通常放声明，源文件放定义：

// add.h
#pragma once
int add(int lhs, int rhs);

// add.cpp
#include "add.h"
int add(int lhs, int rhs) {
    return lhs + rhs;
}

5.2 编译错误、链接错误与运行时装载错误
#

三类错误不要混在一起：

阶段 典型报错 常见原因
编译 not declared、类型不匹配 缺声明、模板实例化失败、语法错误
链接 undefined reference 只声明未定义、漏链接库、ABI/签名不一致
运行时装载 cannot open shared object file 动态库不在搜索路径、架构不匹配

定位符号和依赖的常用命令：

nm -C build/app | less          # 查看并反修饰 C++ 符号
ldd build/app                   # Linux：查看动态库依赖
readelf -d build/app            # 查看 ELF 动态段

在 macOS 上，对应工具通常是 otool -L。

5.3 静态库与动态库
#

  • 静态库（Linux 常见 .a）在链接时把所需代码并入目标文件；部署直接，但产物可能更大；
  • 动态库（Linux .so、macOS .dylib）在装载/运行时解析；可被多个程序共享，但要处理搜索路径与 ABI 兼容。

Linux 动态库搜索会受到二进制的 RPATH/RUNPATH、LD_LIBRARY_PATH、系统缓存与默认目录影响。临时设置 LD_LIBRARY_PATH 适合诊断，不应成为掩盖安装布局问题的长期万能方案。

5.4 ABI：源码兼容不代表二进制兼容
#

ABI（Application Binary Interface）规定二进制层面的调用约定、名称修饰、对象布局和标准库类型实现等。以下情况都可能造成 ABI 不兼容：

  • 编译器或标准库不一致；
  • 编译选项改变对象布局或 C++ ABI；
  • 库升级后导出符号发生变化；
  • Debug/Release 运行库混用；
  • CPU 架构不同。

Python C++ 扩展“能编译但导入失败”时，除了 Python 路径，还要检查扩展和依赖库的 ABI、架构与符号。

5.5 模板：在编译期生成类型特化代码
# 

template <typename T>
T add(T lhs, T rhs) {
    return lhs + rhs;
}

auto i = add(1, 2);        // 实例化 add<int>
auto f = add(1.0f, 2.0f);  // 实例化 add<float>

模板定义通常要放在头文件中，因为编译器在使用点需要看到完整定义才能实例化。CUDA 和高性能计算代码大量使用模板来表达：

  • 数据类型：float、half、bfloat16；
  • tile 大小和线程块配置；
  • 布局与转置选项；
  • 编译期分支和特化实现。

非类型模板参数可以把尺寸变成编译期常量：

template <typename T, std::size_t N>
T sum(const std::array<T, N>& values) {
    T result{};
    for (const T& value : values) {
        result += value;
    }
    return result;
}

模板错误往往很长。定位时从最前面的“用户代码实例化位置”和最底层的真正约束失败开始看，不要被中间几十层展开吓住。

5.6 STL 容器与迭代器
#

类型 内存/访问特征 常见用途
std::vector<T> 连续内存，随机访问 O(1) 数值缓冲区，默认序列容器
std::array<T, N> 固定大小、连续内存 编译期已知的小数组
std::deque<T> 分段存储，两端插入高效 队列、滑动窗口
std::unordered_map<K,V> 哈希表，平均 O(1) 查找 无序键值索引
std::map<K,V> 有序树，O(log n) 需要有序遍历/范围查询

std::vector 扩容可能重新分配内存，使原有指针、引用和迭代器失效：

std::vector<int> values;
values.reserve(1024);  // 已知规模时可减少重复扩容

性能敏感代码除了看大 O 复杂度，还要看连续性、分配次数、缓存局部性和元素大小。很多场景中，线性扫描连续 vector 比理论查找复杂度更低但指针跳转频繁的结构更快。

5.7 最小 CMake 项目
#

目录：

vector_ops/
├── CMakeLists.txt
├── include/vector_ops.h
└── src/vector_ops.cpp

CMakeLists.txt：

cmake_minimum_required(VERSION 3.20)
project(vector_ops LANGUAGES CXX)

add_library(vector_ops src/vector_ops.cpp)
target_include_directories(vector_ops PUBLIC include)
target_compile_features(vector_ops PUBLIC cxx_std_20)

if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
  target_compile_options(vector_ops PRIVATE -Wall -Wextra -Wpedantic)
endif()

构建：

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel

现代 CMake 的核心是 target。用 target_include_directories、target_link_libraries、target_compile_features 描述依赖，少用全局的 include_directories 和手工拼接编译命令。

5.8 C++ 并发的最小认知
#

多个线程并发访问同一内存，其中至少一个写入且缺乏同步，就可能形成数据竞争，属于未定义行为。

#include <mutex>

std::mutex mutex;
int counter = 0;

void increment() {
    std::lock_guard<std::mutex> guard(mutex);
    ++counter;
}

互斥锁保证临界区互斥，原子类型适合简单共享状态，条件变量用于等待状态变化。不要把 volatile 当作线程同步工具；它不提供原子性或线程间 happens-before 关系。

高性能并发优化前，首先保证正确性，并使用 ThreadSanitizer 等工具检查数据竞争。
