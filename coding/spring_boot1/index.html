Spring 框架
#

Spring 如何创建、配置和注入对象
#

要记住下面这些常用的注解：

@Component / @Service：让被扫描到的类交给 Spring 创建和管理。 @ConfigurationProperties：把配置值绑定到对象字段。 @Autowired：主要按类型寻找对象，将对象引用注入字段。 @Data：由 Lombok 生成 getter、setter 等方法，不负责读取配置。

另外，注意到代码里有：

@Autowired
private EmployeeService employeeService;

EmployeeService 虽然是接口，但变量可以引用实现该接口的对象。EmployeeServiceImpl 实现了这个接口，并通过 @Service 和组件扫描注册为 Spring Bean，因此 Spring 可以把匹配的 Bean 注入 employeeService。如果存在多个候选 Bean，需要通过 @Primary、@Qualifier 等规则确定注入哪一个。

进行注释的注解
#

使用下面注解，swagger可以生成可读性更好的接口文档：

注解 说明
@Api 用在类上，例如Controller，表示对类的说明
@ApiModel 用在类上，例如entity、DTO、VO
@ApiModelProperty 用在属性上，描述属性信息
@ApiOperation 用在方法上，例如Controller的方法，说明方法的用途、作用

JWT 拦截器
#

在业务开发中，如果用到JWT，可以使用 JWT 拦截器，来进行请求的校验。

Spring MVC 找到请求对应的处理对象后，在执行 Controller 方法前调用拦截器的 preHandle()。前提是拦截器已注册，且请求路径符合拦截规则。

比如像这样注册一个拦截器，规定它要去拦截的路径：

// 排除登录接口，因为用户需要先登录才能拿到 token
registry.addInterceptor(jwtTokenAdminInterceptor)
        .addPathPatterns("/admin/**")
        .excludePathPatterns("/admin/employee/login");

addInterceptor(...)是让Spring MVC 使用这个对象来拦截请求。进入拦截器以后，我们去判断处理对象（handler）是否代表 Controller 的请求处理方法。如果不是我们就不用去拦截它进行校验：

//判断当前拦截到的是Controller的方法还是其他资源
// instanceof 是 Java 的类型判断运算符,这里判断 handler 是不是一个 HandlerMethod 类型的对象
if (!(handler instanceof HandlerMethod)) {
    //当前拦截到的不是动态方法，直接放行
    return true;
}

后续的逻辑是先从从请求头取 token，然后解析、校验 token，如果成功的话：return true，继续处理。如果失败的话：设置 401，再 return false，停止处理。

全局异常处理器
#

集中处理请求执行过程中出现的异常，将异常转换成统一的接口响应，避免每个 Controller 重复写 try-catch。

抛出异常与处理异常的分工：

  • 抛出异常：中断当前正常执行流程，把失败原因交给上层。
  • 处理异常：记录日志，并将失败原因转换成前端能理解的响应。
  • 异常被处理后，不会回到 throw 的下一行继续执行。
//@RestControllerAdvice：声明这是一个全局 Controller 增强类。
// 配合 @ExceptionHandler，可以统一处理 Controller 请求过程中抛出的异常；方法返回值会写入 HTTP 响应体，通常转换为 JSON。
//@Slf4j：Lombok 注解，自动生成名为 log 的日志对象，因此可以直接调用 log.error(...)
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    // 业务异常：返回明确的业务提示
    @ExceptionHandler(BaseException.class)
    public Result handleBusinessException(BaseException ex) {
        return Result.error(ex.getMessage());
    }

    // 其他异常：记录详细日志，返回统一提示
    @ExceptionHandler(Exception.class)
    public Result handleException(Exception ex) {
        log.error("系统异常", ex);
        return Result.error("系统繁忙，请稍后重试");
    }
}

Exception 可以兜住很多异常，但不同异常需要不同的处理方式。例如，用户名重复应提示“用户名已存在”，程序内部错误则返回统一提示，避免暴露内部细节。因此我们需要异常处理器。

基本流程：请求 → Controller → Service 抛出异常 → 全局异常处理器 → 统一错误响应 → 前端展示提示

ThreadLocal：线程局部变量
#

为每个线程保存各自的数据，实现同一线程内跨方法、跨类读取数据，不同线程的数据相互隔离。它本身不会创建线程。

一个典型的场景：

新增员工时，拦截器从 JWT 中解析出当前登录员工 ID，存入 ThreadLocal；Service 再取出该 ID，设置记录的创建人和修改人，避免通过方法参数逐层传递。（当然用方法参数逐层传递也能实现这个功能）

// 拦截器：保存当前操作人的 ID
BaseContext.setCurrentId(empId);

// Service：获取当前操作人的 ID
employee.setCreateUser(BaseContext.getCurrentId());
employee.setUpdateUser(BaseContext.getCurrentId());

// 请求结束：清理当前线程的数据
BaseContext.removeCurrentId();

在这里，BaseContext 是项目对 ThreadLocal 的封装，对应三个方法：

ThreadLocal 方法 作用
set(value) 设置当前线程的值
get() 获取当前线程的值
remove() 移除当前线程的值

可见一个 ThreadLocal 对象，在每个线程中对应一个值。 同一线程再次调用 set()，会覆盖之前的值；不同线程的值互不影响。但是“一个值”不代表只能保存一个字段，可以使用这样的方法保存不止一个值：

  • 多个 ThreadLocal： 分别保存员工 ID、姓名等数据，使用完需要分别清理。
  • 一个 ThreadLocal 保存对象： 例如 ThreadLocal，对象中可以包含 ID、姓名等多个字段。

注意事项：

  • 使用同一个 ThreadLocal，且运行在同一个线程中，才能读到之前存入的数据。
  • static 表示共享同一个 ThreadLocal 对象，但其中的值按线程隔离。
  • 普通 ThreadLocal 不会自动向新线程或异步任务传递数据；本项目中未设置值时，get() 返回 null。
  • 服务器会复用线程，请求结束后必须清理，避免旧数据残留和不必要的内存占用。同步 Spring MVC 请求通常在拦截器的 afterCompletion 中清理。

Spring MVC 接收前端参数的四种常见写法
#

选哪种写法，先看参数放在哪里，再看后端用单个变量还是对象来接收。

写法 参数来源 作用
@ModelAttribute EmployeePageQueryDTO dto query 参数、表单字段 将多个参数绑定到对象属性
@RequestParam("page") Integer page query 参数、表单字段 接收指定名称的参数
@PathVariable("id") Long id URL 路径 提取路径中的变量
@RequestBody EmployeeDTO dto HTTP 请求体 将请求体内容转换成对象，常用于 JSON

@ModelAttribute：把多个参数装进对象：

前端请求：

GET /employee/page?page=1&pageSize=10&name=张三

后端接收：

@GetMapping("/page")
public Result<PageResult> page(
        @ModelAttribute EmployeePageQueryDTO dto) {
    // dto.getPage()      → 1
    // dto.getPageSize()  → 10
    // dto.getName()      → "张三"
    // ...
}

Spring MVC 按参数名匹配对象属性名，并进行类型转换和属性赋值。 常见 DTO 通过无参构造方法创建，再通过 setter 设置属性；@Data 可以生成 setter。

对于这里的普通 DTO，@ModelAttribute 可以省略：

public Result<PageResult> page(EmployeePageQueryDTO dto)

适用场景：分页查询、多个条件组合查询。

@RequestParam：接收指定的请求参数：

前端请求：

GET /employee/page?page=1&pageSize=10

后端接收：

@GetMapping("/page")
public Result<PageResult> page(
        @RequestParam("page") Integer currentPage,
        @RequestParam("pageSize") Integer pageSize) {
    // currentPage → 1
    // pageSize    → 10
    // ...
}

@RequestParam("page") 的意思是：读取名为 page 的参数，赋给当前方法参数。 常用配置：

// 默认必传；缺少该参数时通常返回 400
@RequestParam("page") Integer page

// 可选；未传时为 null
@RequestParam(value = "name", required = false) String name

// 未传或传入空字符串时，使用默认值 1
@RequestParam(value = "page", defaultValue = "1") Integer page

适用场景：请求参数较少，直接用方法参数接收更清晰。

@PathVariable：接收 URL 路径中的值：

前端请求：

GET /employee/10

后端接收：

@GetMapping("/{id}")
public Result<Employee> getById(@PathVariable("id") Long id) {
    // id → 10L
    // ...
}

这里的 {id} 是路径中的占位符，@PathVariable("id") 将它对应的值取出来。

对比：

/employee/10       → 10 在路径中，用 @PathVariable
/employee?id=10    → id 在 query 中，用 @RequestParam

适用场景：通过 ID 查询、修改或删除某个具体资源。

@RequestBody：接收请求体中的 JSON：

前端请求：

POST /employee
Content-Type: application/json

{
  "name": "张三",
  "phone": "13800138000"
}

后端接收：

@PostMapping
public Result save(@RequestBody EmployeeDTO dto) {
    // dto.getName()  → "张三"
    // dto.getPhone() → "13800138000"
    // ...
}

Spring MVC 通过消息转换器读取请求体；处理 JSON 时，通常由 Jackson 将 JSON 转换成 Java 对象，这个过程叫反序列化。

适用场景：新增或修改数据，前端使用 JSON 提交字段。

普通 DTO 参数省略注解时，不会按这种方式读取 JSON 请求体。 要接收 JSON，通常需要明确写 @RequestBody。

针对四种做法，有容易混淆的地方：

  • 不是 GET 一定用 @RequestParam，POST 一定用 @RequestBody。 判断依据是参数所在位置和内容格式。POST 请求也可以带 query 参数。
  • 同一个接口可以组合使用这些注解。 例如修改员工时，用 @PathVariable 接收路径中的员工 ID，用 @RequestBody 接收 JSON 中的修改内容。
  • 绑定不等于校验。 参数成功装进 DTO，不代表必填、长度等条件都已检查；这些通常还需要配合 @Valid 和字段上的校验注解。

记忆：多个查询条件装 DTO，指定请求参数用 @RequestParam，路径取值用 @PathVariable，JSON 请求体用 @RequestBody。

PageHelper 分页查询
# 

// 设置页码（从 1 开始）和每页条数，本身不查询数据库
PageHelper.startPage(dto.getPage(), dto.getPageSize());

// 执行查询：插件自动查询总数，并为 SQL 添加分页限制
Page<Employee> page = employeeMapper.pageQuery(dto);

long total = page.getTotal();               // 符合条件的总记录数
List<Employee> records = page.getResult();  // 当前页的数据

startPage() 将分页参数保存在当前线程的 ThreadLocal 中，MyBatis 拦截器读取参数并处理分页。

注意PageHelper.startPage应该紧挨着目标 Mapper 查询调用，作用于之后的第一个 MyBatis 查询；之后的 Mapper SQL 就无须手写 LIMIT。

查询结果得到Page<E>，既保存本页数据，也保存分页信息。这个示例page使用getTotal() 和 getResult() 不会再次查询数据库。

业务逻辑
#

一次完整的登录请求
#

前端提交账号密码 → Controller 接收 DTO，进行参数校验 → Controller 调用 Service → Service 调用 Mapper，按账号查询数据库 → Mapper 返回 Employee（未找到则返回空） → Service 判断账号是否存在，校验密码和账号状态 → 校验通过后生成 JWT token → 组装 VO，通过 Result 返回前端

总体来说，登录负责签发 Token，前端负责携带 Token，拦截器负责校验 Token。后面写新的一系列 Controller 时，不需要每个方法都重复写“是否登录”的判断，拦截器会在进入这些方法之前统一处理。

Java知识
#

Builder 模式
#

它的思路是：先一步步设置所需信息，最后生成结果。你先拿到一个构建器，告诉它数据、签名方式和过期时间（你需要放入这个实例的信息），然后由它返回给你一个构建好的示例。

builder() 本身也是普通的方法调用。 方法内部可以使用 new 创建构建器，只是把创建细节封装起来了。Builder 并没有取代 new。

@Builder 会帮你生成构建器类、获取构建器的方法、设置字段的方法，以及最终创建对象的 build() 方法

可以这么理解：new 负责实例化，@Autowired 负责注入，Builder 负责组织构建过程。

链式调用
#

链式调用的关键：前一个方法返回的对象，可以继续调用下一个方法。来看代码：

JwtBuilder builder = Jwts.builder() // 返回构建器对象
    .setClaims(claims) // 设置数据，再返回构建器对象
    .signWith(signatureAlgorithm, secretKey.getBytes(StandardCharsets.UTF_8)) // 设置签名方式，再返回构建器对象
    .setExpiration(exp); // 设置过期时间，再返回构建器对象

这里几个配置方法返回的是当前 JwtBuilder，所以可以连续配置同一个构建器。这里的每一个点，都是在调用前一步返回的对象的方法。

等价于：

JwtBuilder builder = Jwts.builder();

builder.setClaims(claims);
builder.signWith(
        signatureAlgorithm,
        secretKey.getBytes(StandardCharsets.UTF_8)
);
builder.setExpiration(exp);

只要前一个方法返回的对象能调用下一个方法，就可以链式调用。比如：

class Student {
    private String name;
    private int age;

    public Student setName(String name) {
        this.name = name;
        return this; // 返回当前这个对象
    }

    public Student setAge(int age) {
        this.age = age;
        return this; // 返回当前这个对象
    }
}

// 支持链式调用
Student student = new Student()
        .setName("小明")
        .setAge(18);

如果上面的方法返回的是void，那么就不能用链式调用。
