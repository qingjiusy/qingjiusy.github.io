模型和优化器都就位后，最后一块拼图是喂数据：把磁盘上一条很长的 token 流，切成一个个 (batch, context_length) 的小窗口喂给模型；以及把训练到一半的 model + optimizer + iteration 存成 checkpoint、之后能原样恢复。这两件事看似琐碎，却是"能不能真正跑起一次训练"的关键。

学习目标
#

  1. 建立语言模型训练数据 = 一条很长的 token 流的心智模型。
  2. 理解输入与标签错位一位（label 是 next-token）——本章最核心的直觉。
  3. 知道 token id 为什么要用 int64（long）、为什么磁盘上常存 uint16。
  4. 理解 np.memmap 如何让超大数据不必整体读进内存，按索引取窗口。
  5. 掌握 checkpoint 往返的 torch 机制：state_dict + torch.save/load + load_state_dict。

1. 训练数据是一条"很长的 token 流"
#

预训练数据经过 tokenizer 之后，不再是一句句独立的句子，而是首尾相接拼成一维整数序列，比如 [15, 923, 7, 402, 88, ...]，长度可能是几十亿。训练时我们做的是自回归语言建模：给定前面若干个 token，预测下一个 token。

所以从这条流里采一个样本，就是：

  • 随机选一个起点 s；
  • 取长度 context_length 的一段作为输入 input；
  • 把这段整体右移一位的那一段作为标签 label。

也就是说 label[i] 恰好是 input[i] 的下一个 token —— 这就是 next-token prediction 的监督信号。下面用一条玩具流 [0..19] 把这个"错位一位"看个清楚（这里只演示单个窗口的概念，不是完整采样器）。

# 玩具 token 流：用 0..19 当"token id"，方便肉眼追踪错位关系
stream = np.arange(0, 20)
context_length = 5

# 概念演示：固定选一个起点，取一个窗口和它"右移一位"的标签窗口
s = 3
input_window = stream[s : s + context_length]
label_window = stream[s + 1 : s + 1 + context_length]

print("整条流   :", stream)
print(f"起点 s   : {s},  context_length = {context_length}")
print("input    :", input_window)
print("label    :", label_window)
print("label 是不是 input 右移一位?  ", np.array_equal(label_window, input_window + 1))
print("\n直觉：看到 [3,4,5,6,7] 时，模型要依次预测 [4,5,6,7,8]。")

2. dtype 与 device：为什么 token id 要用 int64 (long)
#

两个容易被忽略但会直接报错的细节：

  • dtype：token id 是索引，要拿去 Embedding 查表。PyTorch 的索引/嵌入要求索引张量是整型（torch.long = int64），喂浮点会直接抛错。另外，磁盘上为了省空间常把 token 存成 uint16（词表 < 65536 时够用），但取出来喂模型前必须转成 long。
  • device：采出来的 batch 要和模型在同一个 device 上，否则前向会报 “expected all tensors on the same device”。所以 get_batch 有个 device 参数——测试里还特意用非法的 cuda:99 检验你确实把张量搬了过去。

下面看嵌入对 dtype 的要求。

emb = nn.Embedding(num_embeddings=20, embedding_dim=3)

ids_long = torch.arange(5)              # 默认就是 int64 = long
print("torch.arange(5).dtype :", ids_long.dtype)
print("用 long 索引嵌入 -> 输出 shape:", tuple(emb(ids_long).shape))

# 磁盘上常见的 uint16 -> 必须先转成 long 才能查表
ids_u16 = np.array([1, 2, 3], dtype=np.uint16)
print("\n磁盘存储 dtype        :", ids_u16.dtype)
ids_cast = torch.from_numpy(ids_u16).long()
print("转成 torch 索引 dtype :", ids_cast.dtype)

# 反例：用浮点当索引会报错
try:
    emb(ids_long.float())
except Exception as e:
    print("\n浮点当索引 ->", type(e).__name__, ":", str(e).splitlines()[0])

3. 随机起点采样（通用机制）
#

一个 batch 由 batch_size 个独立随机的起点决定。合法起点的范围是关键：窗口要取 input 和右移一位的 label，所以最大起点必须保证 s + context_length 仍在流内。想一想——起点应该从哪个区间里取？ 下面用 np.random.randint 演示这个采样机制本身（注意这只是"怎么随机取整数"，还不是完整的 get_batch）。

test_data.py 会统计上千次采样里每个起点出现的频次，检验：(1) 采样确实均匀随机，(2) 从不越界（最大起点 = len(dataset) - context_length - 1）。所以边界差一位就会挂——这正是要你自己想清楚的地方。

dataset_len = 100
context_length = 7
batch_size = 32

# np.random.randint(low, high, size) 从 [low, high) 取整数——high 是开区间
starts = np.random.randint(0, dataset_len - context_length, size=batch_size)
print("一批随机起点 (batch_size 个):")
print(starts)
print("\n最小起点:", starts.min(), " 最大起点:", starts.max())
print("此处传入的 high =", dataset_len - context_length,
      "(randint 的 high 是开区间)")
print("思考：这个 high 传对了吗？test_data.py 期望能取到的最大起点是多少？自己对一下。")

回答：传对了，因为np.random.randint(low, high) 的 high 是开区间，所以high = dataset_len - context_length，对应到实际上能取的最大值就是dataset_len - context_length - 1，所以代入以后计算可得期望的最大能取到的起点就是 92，没有问题。

4. np.memmap：不整体载入也能按索引取窗口
#

真实数据集有几十上百 GB，np.load 全读进内存会直接 OOM。np.memmap（或 np.load(..., mmap_mode="r")）把文件映射到虚拟地址空间：你像操作普通数组一样索引它，操作系统只在你真正访问某段时才把那几页从磁盘调进内存。切一个 context_length 的窗口，只会碰到那一小段。

下面在 /tmp 造一个小的 memmap 文件，演示"写入 → 只读重开 → 按索引读一个窗口"。

import os
path = "/tmp/cs336_toy_tokens.bin"

# 1) 写：造一条 1000 个 token 的流，存成 uint16 的 memmap 文件
mm_write = np.memmap(path, dtype=np.uint16, mode="w+", shape=(1000,))
mm_write[:] = np.arange(1000, dtype=np.uint16)
mm_write.flush()
del mm_write   # 关闭写句柄

# 2) 只读重开：注意这一步几乎不占内存，没有把 1000 个数全读进来
data = np.memmap(path, dtype=np.uint16, mode="r")
print("type          :", type(data).__name__)
print("dtype / shape :", data.dtype, "/", data.shape)
print("文件大小       :", os.path.getsize(path), "bytes  (=1000 * 2 bytes)")

# 3) 只取一个窗口——只有这一小段会被真正读进内存
s = 500
window = data[s : s + 7]
print(f"\n从下标 {s} 读一个长度 7 的窗口:", np.asarray(window))
print("整体保持在磁盘上，按需分页读取 —— 这就是 memmap 处理超大数据的方式。")

5. Checkpoint 往返（通用 torch 机制）
#

训练可能跑几小时甚至几天，中途要能存档、断点续训。一个 checkpoint 至少要存三样东西，缺一不可：

  • 模型参数 model.state_dict()
  • 优化器状态 optimizer.state_dict() —— AdamW 的一阶/二阶动量都在这里，不存的话续训等于重启动量；
  • 迭代步数 iteration —— 恢复后学习率调度、日志才能接着走。

机制就是标准 torch 三件套：把它们打包成一个 dict 用 torch.save 落盘；恢复时 torch.load 读回来，再分别 load_state_dict 灌回已经构造好的 model / optimizer。下面用一个极小的模型演示这套往返（通用机制，不是 run_save/load_checkpoint 的交付实现）。

# 极小玩具模型 + 优化器，先走一步产生一些优化器状态
torch.manual_seed(0)
toy = nn.Linear(4, 2)
opt = torch.optim.AdamW(toy.parameters(), lr=1e-2)

x = torch.randn(3, 4)
loss = toy(x).pow(2).sum()
loss.backward()
opt.step()

# --- 保存：打包成 dict 落盘 ---
ckpt_path = "/tmp/cs336_toy_ckpt.pt"
torch.save(
    {"model": toy.state_dict(),
     "optimizer": opt.state_dict(),
     "iteration": 7},
    ckpt_path,
)
print("已保存 checkpoint:", ckpt_path)
print("字典的键:", ["model", "optimizer", "iteration"])

已保存 checkpoint: /tmp/cs336_toy_ckpt.pt
字典的键: ['model', 'optimizer', 'iteration']

# --- 恢复：先构造同结构的 model/optimizer，再灌状态 ---
new_toy = nn.Linear(4, 2)
new_opt = torch.optim.AdamW(new_toy.parameters(), lr=1e-2)

# 恢复前：两个模型的权重不同
before = torch.allclose(new_toy.weight, toy.weight)

loaded = torch.load(ckpt_path, weights_only=False)  # 自己存的文件
new_toy.load_state_dict(loaded["model"])
new_opt.load_state_dict(loaded["optimizer"])
restored_iter = loaded["iteration"]

after = torch.allclose(new_toy.weight, toy.weight)
print("恢复前权重相同?", before)
print("恢复后权重相同?", after)
print("恢复出的 iteration:", restored_iter)
print("\n往返成功：model / optimizer / iteration 都完好回来了。")
print("注：weights_only 是 torch 2.6 的安全开关——加载他人文件时要当心。")

6. ✏️ 你的任务：get_batch 引导骨架
#

把前面几块拼起来就是采样器了。下面是给你填的骨架（... 处留白，不可直接运行）。逐步想清楚：合法起点区间是什么？input 窗口和 label 窗口的切片差在哪？最后 dtype 和 device 怎么处理？

建议先在上面那条 [0..19] 玩具流上手验证一个 batch，确认 y == x + 1 再去跑 test_data.py。

def get_batch(dataset, batch_size, context_length, device):
    # step 1: 采 batch_size 个随机起点
    # 想清楚合法区间：要能取到 input 和"右移一位"的 label，最大起点是多少？
    # 由于labels的存在，所以能取到的最后一位一定是在 dataset_len - context_length - 1
    # 而 np.random.randint(low, high, size)，其中 high 是开区间，所以就是：
    starts = np.random.randint(0, len(dataset) - context_length, size=batch_size) # (batch_size, )

    # step 2: 对每个起点，取长度 context_length 的输入窗口，堆成 (batch_size, context_length)
    # dataset 和 starts 目前都是 numpy中的对象
    # np.stack 和 torch.stack 非常像，np.stack([a, b], axis=0) 就类似于 torch.stack([a, b], dim=0)
    inputs = np.stack([dataset[s : s + context_length] for s in starts], axis=0) # (batch_size, context_length)

    # step 3: 取"右移一位"的标签窗口（label 是 next-token）
    labels = np.stack([dataset[s + 1 : s + context_length + 1] for s in starts], axis=0) # (batch_size, context_length)

    # step 4: 转成 torch.long，并搬到 device 上（两者都要在同一 device）
    x = torch.tensor(inputs, dtype = torch.int64, device = device)
    y = torch.tensor(labels, dtype = torch.int64, device = device)

    return x, y

7. ✏️ 你的任务：save_checkpoint / load_checkpoint 引导骨架
#

对照第 5 节的机制，把它包成两个函数。注意 load 要返回 iteration，并且是把状态灌进外面传进来的 model / optimizer（不是新建）。

def save_checkpoint(model, optimizer, iteration, out):
    # step 1: 把 model / optimizer 的 state_dict 和 iteration 打包成一个 dict
    obj = {
        "model":model.state_dict(),
        "optimizer": optimizer.state_dict(),
        "iteration": iteration
    }
    
    # step 2: torch.save(obj, out)
    torch.save(obj, out)


def load_checkpoint(src, model, optimizer):
    # step 1: torch.load 读回字典
    obj = torch.load(src)

    # step 2: 分别把状态灌回传入的 model / optimizer（load_state_dict）
    model.load_state_dict(obj["model"])
    optimizer.load_state_dict(obj["optimizer"])

    # step 3: 返回存档时的 iteration
    return obj["iteration"]

🔬 拓展实验（自己动手，加深理解）
#

  1. 边界对拍：在玩具流上把起点上界故意 +1（越界一位），观察什么时候会取到超出流末尾的标签、或索引越界报错。这能让你彻底记住合法区间。
  2. y == x + 1 自检：写完 get_batch 后，先喂 np.arange(0, 20) 这种"id 就是位置"的流，断言 torch.equal(y, x + 1)。玩具流上过了，再上真实数据。
  3. memmap 省内存：用 np.memmap 打开一个大文件后，观察进程内存（htop 或 psutil）在"打开"与"访问某段"前后的变化，体会按需分页。
  4. 不存优化器状态会怎样：故意只保存 model.state_dict()、丢掉 optimizer 状态，续训几步看 loss 曲线是否出现"抖动/重启动量"的痕迹，理解为什么优化器状态必须一起存。
  5. device 检验：想想 test_data.py 为什么要用 cuda:99 这个非法设备来测你——它在检查你到底有没有把张量搬到 device 上。

回答
#

  1. 略
  2. 略
  3. np.memmap 通过内存映射（memory mapping）访问大文件，而不是在打开文件时就把全部数据读入进程内存。因此，即使文件很大，刚执行 np.memmap(...) 时进程的实际内存占用通常只会增加很少；当真正访问其中某一段数据时，操作系统才会通过按需分页（demand paging）把对应的数据页从磁盘加载到物理内存中，此时内存占用才会逐渐增加。相比 np.fromfile 等一次性把整个文件读入内存的方式，memmap 特别适合处理远大于可用内存的大规模数据集，其核心优势就是：**只加载当前实际需要访问的数据，而不必让整个文件同时驻留在内存中。**整个大文件只占虚拟地址空间，真正占用多少物理内存主要取决于当前实际访问了哪些页，以及操作系统保留了多少缓存。
  4. 如果续训时只恢复 model.state_dict()，而不恢复 optimizer.state_dict()，模型参数虽然会从断点处继续，但优化器内部积累的历史信息会全部丢失。以 AdamW 为例，一阶矩 m_t、二阶矩 v_t 以及当前 step 都会重新初始化，相当于优化器“失忆”后重新开始估计梯度方向和尺度。因此续训最初几步的更新方向和有效步长可能突然发生变化，使 loss 曲线出现短暂的抖动、跳变或类似重新启动的现象。对于 SGD + Momentum，也会因为动量缓存被清空而出现“重新积累动量”的过程。因此，如果希望训练能够真正从 checkpoint 无缝继续，通常必须同时保存并恢复 模型参数 + 优化器状态 + 当前训练步数。
  5. test_data.py 使用 cuda:99 这种明显不存在的设备，是为了检查你的代码是否真的执行了“把数据移动到指定 device”这一步。如果你的实现完全忽略 device 参数，测试可能反而不会报错，因为张量始终留在 CPU；但如果你正确写了类似 tensor.to(device) 的逻辑，那么传入 cuda:99 时就应该因为设备不存在而失败。换句话说，这个测试不是在要求 cuda:99 能运行，而是在利用一个非法设备作为探针，验证你的 device 参数有没有真正参与数据搬运。核心要点是：不要只在函数签名里接收 device，而要确保最终产生的张量确实被移动到该设备上。

小结
#

  • 训练数据是一条很长的 token 流；采样 = 随机起点 + 长度 context_length 的窗口。
  • label 是 input 右移一位（next-token）——本章最核心的直觉，务必在玩具流上验证 y == x + 1。
  • token id 用 int64（long） 查嵌入；磁盘常存 uint16，取出后要转 long；batch 要和模型同 device。
  • np.memmap 让超大数据按需分页读取，不必整体进内存。
  • checkpoint = state_dict + torch.save/load + load_state_dict，必须同时存 model / optimizer / iteration。
